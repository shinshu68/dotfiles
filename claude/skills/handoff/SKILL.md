# handoff — 次の作業を新しいセッションに引き継ぐ

## なぜこのスキルがあるか

1つの作業（実装 → /lgtm → コミット → /pr → マージ → /pr-done）を終えたセッションには、もう不要になった試行錯誤や差分・ログが大量に残っている。そのまま次の作業を始めると、コンテキストが圧迫されて精度が落ち、前の作業の文脈に引きずられやすい。そこで次の作業は `/clear` した新しいセッションで始めたい。

ただし Claude は `/clear` を自分で実行できないし、クリアすると「次に何をやるか」の文脈も消える。そこでこのスキルは、**クリア後の自分が迷わず着手できるだけの情報を引き継ぎメモに書き出して止まる**。ユーザーが `/clear` → `/kickoff` と打つと、新しいセッションの Claude がメモを読んで作業を始める。

## 手順

### 1. 引き継ぐ作業を特定する

直前の Claude の応答（pr-done の「次は〜〜を進めます。」など）で提案されていた次の作業を、会話の流れから特定する。

- 提案が1つだけ → それを引き継ぐ。
- 番号付きの選択肢が複数ある → 引数に番号があればそれ、なければ Claude が推奨していたもの、それもなければ最初の選択肢。どれを選んだか報告で一言触れる。
- 引数にテキストがある（例:「/handoff テストは後回しで」）→ 作業内容の補足・条件としてメモに反映する。
- 次の作業が会話から読み取れない → 推測でメモを作らず、「次に何の作業を引き継ぎますか？」と短く聞く。中身の薄いメモでクリアさせると、新しいセッションで迷子になるため。

### 2. 引き継ぎメモを書く

クリア後の Claude は**この会話を一切覚えていない**。その Claude がメモだけを読んで、ユーザーに聞き返さずに作業を始められるかを基準に書く。一方で、終わった作業の経緯まで書き写すとクリアする意味が薄れるので、次の作業に効くことだけに絞る。

以下のテンプレートを使う（該当がない項目は行ごと省く）:

```markdown
---
name: handoff
description: /kickoff で着手する次の作業の引き継ぎメモ（一時ファイル。着手時に削除する）
type: project
---

# 引き継ぎ: <作業のタイトル>

- 作成: <YYYY-MM-DD HH:MM>
- リポジトリ: <リポジトリのルートの絶対パス>
- 開始時のブランチ: <例: develop（pr-done で最新化済み）>
- バックログ: <例: #012（未着手）>

## やること
<作業の目的と完了条件を2〜5行。何ができたら終わりか>

## 背景・決まっていること
- <ユーザーと合意した方針、仕様、命名、やらないと決めたこと など>

## 関連ファイル・参照先
- <パス>: <なぜ関係するか>

## 着手手順
1. <最初の一歩。例: develop から feature/xxx を切る / `/backlog` で #012 に着手する>
2. ...

## 注意点・未決事項
- <ユーザーに確認が必要なこと、ハマりどころ>
```

書くときのポイント:
- 「さっきの件」「例のファイル」のような、この会話を前提にした表現は使わない。具体的な名前・パス・ID で書く。
- バックログタスクに紐づく作業ならタスクIDを必ず書く（クリア後の Claude は /backlog で着手するため）。
- ユーザーがこの会話中に述べた条件・好み（「テストは後回し」など）は「背景・決まっていること」に残す。これが一番失われやすい情報。

### 3. 自動メモリに保存する

保存先は Claude Code の自動メモリのディレクトリ（システムプロンプトで案内されている memory ディレクトリ。通常は `~/.claude/projects/<プロジェクト>/memory/`）。

1. 引き継ぎメモを `handoff.md` として保存する。既に `handoff.md` がある場合は、着手されずに残った古い引き継ぎなので上書きし、報告でその旧タイトルに一言触れる。
2. `MEMORY.md`（索引）に次の1行を追加する（既に同じ行があれば重複させない）:

   ```
   - [引き継ぎ: <作業のタイトル>](handoff.md) — 一時メモ。ユーザーが /kickoff を実行したときだけ読んで着手する
   ```

   `MEMORY.md` は新しいセッションの開始時に自動で読み込まれるので、クリア後の Claude は引き継ぎの存在を最初から知っている。「/kickoff のときだけ」と書いておくのは、クリア後に別の話をしたいだけのユーザーに対して、勝手に作業を始めないため。

**自動メモリが使えない場合**（システムプロンプトに memory ディレクトリの案内がない、autoMemoryEnabled が false など）は、`~/.claude/handoff/<リポジトリ名>.md` に同じ内容で保存する（索引への追記はしない）。どちらに保存したかは報告に含める。

### 4. ユーザーに案内して止まる

次の作業には**着手しない**。ブランチを切る、ファイルを編集する、/backlog で着手状態にする、といったことはクリア後の /kickoff の役目。ここで始めてしまうと、クリアで中途半端な状態の文脈が失われる。

報告は短く、次の形にする:

> 「<作業のタイトル>」の引き継ぎメモを保存しました。
> `/clear` してから `/kickoff` を実行してください。

保存先のパスや、メモの要点（2〜3行）は添えてよい。メモ全文の貼り付けは不要。

## 注意

- 未コミットの変更が残っている場合は、`/clear` しても作業ツリーは消えないが、どの変更が何のためのものかという文脈は消える。`git status` で変更が見えたら、その旨を報告に一言添える（コミットするかどうかはユーザーの判断）。
- `MEMORY.md` の既存の内容は変更しない。追加するのは引き継ぎの1行だけ。
