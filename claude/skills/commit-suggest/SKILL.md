# コミットメッセージ提案 (commit-suggest)

## これは何をするスキルか

ステージされているgitの変更内容を読み、その変更が「何を」「なぜ」行っているかを理解した上で、
gitmoji付きのタイトルと日本語の本文からなるコミットメッセージ案を **3つ** 作ってチャットに提示する。
`git commit` の実行はしない。ユーザーが気に入った案を選び、自分の手でコミットする前提。

なぜ3案なのか: 同じ差分でも「ユーザー視点で何が変わったか」「実装上何をしたか」「簡潔な要約」など、
切り口によって適切な粒度や言葉選びは変わる。1案だけ出すと的外れだった時にやり直しのコストが高いので、
角度の違う3案を出してユーザーに選んでもらう方が実用的。

## 手順

### 1. ステージ済みの変更を確認する

まず次を実行し、何がステージされているかを把握する。

```
git status --short
git diff --staged --stat
```

- ステージされた変更が一件もない場合は、その旨をユーザーに伝えて止まる。`git status` の内容(未ステージの変更や未追跡ファイル)を見せて、「先に `git add` してください」と案内する。ユーザーから明示的に頼まれない限り、未ステージの変更を勝手に対象にしない — ユーザーが意図的に一部だけステージしている可能性があるため。
- 差分がロックファイルや自動生成ファイルばかりの場合はその旨を一言添え、実質的な変更が他にあればそちらを中心に読む。
### 2. 差分の中身を読み、変更の意図を理解する

```
git diff --staged
```

diffが大きい場合は、ファイルごと・意味のあるまとまりごとに読む。単に「どの行が変わったか」ではなく、
「なぜこの変更が必要だったのか」「どんな問題を解決しているのか」を考える。ファイル名・関数名・コメント・
周辺コードから意図を推測してよいが、diffに現れていない事実を勝手に作り出さない。

参考になりそうなら直近のコミットログも見ておくと、そのリポジトリでの言葉選びの雰囲気がつかめる。

```
git log --oneline -10
```

### 3. gitmojiを選ぶ

**絵文字の文字そのものではなく、`:sparkles:` のような gitmoji のコード表記をタイトルの先頭に
使うこと**(実際の絵文字グリフは使わない)。変更内容に最も合うものを、下の対応表から選ぶ。

| コード | 用途 |
|---|---|
| `:sparkles:` | 新機能の追加 |
| `:bug:` | バグ修正(既存動作は壊れていなくても、防御的なチェック追加など「気づいていなかった不具合を直した」と言えるものを含む) |
| `:recycle:` | 挙動を変えないリファクタリング |
| `:memo:` | ドキュメント・コメントの追加/修正 |
| `:lipstick:` | UI・見た目・スタイルの調整(ロジック変更なし) |
| `:zap:` | パフォーマンス改善 |
| `:white_check_mark:` | テストの追加・修正 |
| `:wrench:` | 設定ファイル・ビルド構成の変更 |
| `:fire:` | コード・ファイルの削除 |
| `:truck:` | ファイル・ディレクトリの移動/リネーム |
| `:arrow_up:` / `:arrow_down:` | 依存パッケージのアップグレード/ダウングレード |
| `:lock:` | セキュリティ関連の修正 |
| `:ambulance:` | 緊急のホットフィックス |
| `:art:` | コードの構造・フォーマットの改善(コードスタイル) |
| `:construction:` | 作業中(WIP)のコミット |
| `:globe_with_meridians:` | 国際化・ローカライゼーション |
| `:green_heart:` | CIの修正・改善 |
| `:twisted_rightwards_arrows:` | ブランチのマージ |
| `:rewind:` | 変更の取り消し(revert) |
| `:card_file_box:` | データベース関連の変更(スキーマ・マイグレーション) |
| `:bookmark:` | リリース・バージョンタグ |
| `:technologist:` | 開発者体験(DX)の改善(スクリプト・ツール類) |

判断に迷ったときの優先順位の目安: バグを直しているなら `:bug:`、ユーザーが触れる新しい機能なら
`:sparkles:`、それ以外で挙動を変えていないなら `:recycle:` か `:art:`、ドキュメントのみなら `:memo:`。

3つの候補は基本的に同じ変更に対する言い換えなので同じgitmojiになることが多いが、変更が複数の性質を
またぐ場合(例: バグ修正のついでにリファクタもした)は、候補ごとに異なる切り口・異なるgitmojiで
提示してもよい。

### 4. 3つの候補を作る

各候補は次の形式にする。

```
<gitmojiコード> <タイトル(日本語、命令形、目安50字以内、末尾に句点は付けない)>

<本文(日本語、1〜3文)>
```

タイトルは「何をしたか」を一目でわかる短い言葉にする。

**本文は適度な長さで改行を入れること。** 1行に長々と書き続けず、全角35〜40字程度(git の慣習である
半角72字ルールに相当する目安)で改行を入れる。`git log` やエディタの多くはこの幅を前提に表示するため、
改行のない長い1行は読みにくくなる。文の区切り(句点)がよい改行位置になることが多いが、1文が長い
場合は文の途中でも意味の区切りで改行してよい。逆に、改行を細かく入れすぎて1〜2文節ごとに改行する
必要もない — あくまで「読みやすい行の長さ」が目的であって、詩のような改行にしないこと。

**本文の最重要ルール: 「何をしたか」ではなく「なぜしたか」を書く。** タイトルとdiffを見れば
「何が変わったか」はすでにわかる。本文でそれをもう一度言い換えても情報量がゼロなので、必ず
「どんな問題・不便・要望に対応するための変更か」「なぜこのタイミング・この形で必要だったか」を書く。
diffの内容(関数名・ファイル名・追加した処理の説明)を並べ直しただけの文は本文として不十分。

これは案2(実装視点)でも同じ。「実装視点」というのは書く粒度(どのファイル・どの関数に触れたか)
を変えるという意味であって、本文の中身を「何をしたか」の説明に差し替えてよいという意味ではない。
案2でも、なぜその実装アプローチを選んだのか・なぜそこに手を入れる必要があったのかを書く。

もしdiffやコミット内容から「なぜ」が全く読み取れない場合(理由がコード上に一切手がかりがない)は、
無理に理由を創作せず、素直に「何をしたか」を簡潔に書いてよい。ただし多くの変更には、コメント・
変数名・追加されたチェックの内容などから推測できる理由があるはずなので、まずそれを探すこと。

3案は切り口を変える。例えば:

- 案1: ユーザー・利用者への影響を軸にした「なぜ」の説明
- 案2: 実装・技術的な事情を軸にした「なぜ」の説明(ただし内容は依然として「なぜ」)
- 案3: もっとも簡潔な要約(本文は1文程度、それでも「なぜ」を核にする)
ただし切り口を変えるために事実を誇張したり、diffにない内容を付け加えたりしないこと。あくまで同じ
変更を異なる角度から正確に言い換える。

### 5. 提示する

出力の形式は毎回そろえること。ばらつきがあると、ユーザーが読む場所を探し直したりコピーしづらかった
りする。**候補全体、あるいは候補ごとにコードブロック(```)で囲まない。** コードブロックは表示幅に
合わせて自動で折り返されないため、チャットやターミナルの表示が狭いと横スクロールしないと全文を
読めなくなり、実用上とても不便になる。代わりに、通常のMarkdownの見出しと段落としてそのまま出力する
— これなら表示幅に合わせて自然に折り返される。

出力は次の並びに固定する(`###` は実際に見出しとして書く。以下はテンプレートを示すための引用であり、
実際の回答自体をこの外枠のコードブロックで囲むという意味ではない)。

```
### 候補1
<gitmojiコード> <タイトル>

<本文>

### 候補2
<gitmojiコード> <タイトル>

<本文>

### 候補3
<gitmojiコード> <タイトル>

<本文>
```

`### 候補N` の見出し・その下のタイトル行・空行・本文、という並びを普通の地の文として書く。タイトル行や
本文を等幅フォントにする必要はなく、通常のテキストでよい。ユーザーはタイトル行と本文をそのままコピー
してコミットメッセージとして使う想定なので、余計な装飾(引用符で囲む、絵文字グリフに変換する等)は
付けない。ファイルとして保存する必要はない(頼まれない限り)。

**このスキルは `git commit` を実行しない。** 候補を出すところまでが役目で、どれを使うか・実際に
コミットするかはユーザーが判断する。

## 出力例

以下は実際にユーザーへ返す回答そのものの見た目(コードブロックには入れない)。

### 候補1
:sparkles: ユーザー設定画面にダークモード切り替えを追加

夜間や暗い環境での利用時に、明るいテーマだと目が疲れるという
声があったため、テーマを切り替えられるようにした。

### 候補2
:sparkles: settings.tsx にテーマ切り替えのUIとstate管理を追加

既存のSettings関連コンポーネントに閉じた形で状態を持たせたかった
ため、グローバルなstore経由ではなくローカルなstateとして実装した。

### 候補3
:sparkles: ダークモード切り替え機能を追加

長時間利用時の目の疲れを軽減するため。

## 注意点

- 対象はあくまで `git diff --staged` の内容。未ステージの変更やuntrackedファイルは含めない。
- 差分が明らかに複数の関心事(例: 無関係な2つの機能追加)を含んでいる場合は、その旨を一言指摘し、
  「本来はコミットを分けた方がよいかもしれません」と伝えてよい。ただしその場合も、まずは今ステージ
  されている内容に対して3案を出す。
- gitリポジトリでない、またはgitが使えない場合はその旨を伝えて止まる。
- タイトルには必ずgitmojiのコード表記(例: `:sparkles:`)を使い、絵文字グリフそのものは使わない。
- 本文は「何をしたか」の言い換えにしないこと。必ず「なぜ」を書く。3案とも本文の切り口(視点)は変えてよいが、「なぜ」を書くという原則は3案共通で外さない。
- 本文は全角35〜40字程度を目安に改行を入れ、1行に長く書き続けないこと(候補3のように本文が1文で収まる場合は改行不要)。
- 出力全体をコードブロック(```)で囲まないこと。横幅の狭い環境で横スクロールが必要になり読みにくくなるため、通常のMarkdown(見出し・段落)としてそのまま提示する。
