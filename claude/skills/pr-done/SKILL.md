# pr-done

GitHub上でPRを手動マージした後の後片付け（developの同期 + マージ済みブランチの削除 + 対応するバックログタスクの完了）を行うスキルです。

## いつ使うか

- ユーザーが `/pr-done` と入力したとき
- 「PRマージしたからdevelopに反映して」「developを最新化して」「マージ済みのブランチ削除して」など、PRマージ後の後片付けを依頼されたとき

このスキルは **PRを手動でマージした後** に使うことが前提です。PRの作成自体はこのスキルの範囲外です（prスキルなど別のスキルを使ってください）。

## 最初に判断すること: どのPRがマージされたか

マージされたPRの向き先によって、やることが変わります。会話の流れ（`pr` スキルで作成したPR、ユーザーの発言など）から判断してください。

- **develop → main のPR（リリースPR）をマージした後** → 「バックマージモード」。後述の「バックマージモード」を実行する。
- **それ以外（featureブランチなど → develop のPR）をマージした後** → 「通常モード」。下記「何をするか」を実行する。
- どちらか判断できない場合は、`gh pr list --state merged --limit 3` などでマージ済みPRのbase/headを確認するか、ユーザーに一言確認する。決め打ちしない。

## 何をするか（通常モード）

1. 未コミットの変更がないか確認する（あれば安全のため中断する）
2. ローカルの `develop` ブランチに切り替える
3. `origin/develop` の最新を `git pull` で取り込む
4. `develop` にマージ済みのローカルブランチを `git branch --merged develop` で洗い出す
5. `develop` / `main` / `master` は保護し、それ以外のマージ済みブランチを `git branch -d`（安全な削除）で削除する
6. マージされたPRに対応するバックログタスクを特定し、`/backlog` スキルで完了にする（詳細は下記「バックログタスクの完了」を参照）
7. 続きの作業が見えていれば「次は〜〜を進めます。」と提案して止まる。実際には着手しない（詳細は下記「完了後の振る舞い」を参照）

削除は確認なしで自動的に行いますが、`git branch -d` は「developに未マージのブランチ」を削除できない安全なコマンドなので、作業中のブランチを誤って消す心配はありません。

このスキルはローカルブランチのみを対象とし、リモート（`origin`）のブランチには一切手を出しません（詳細は下記「注意点・エッジケース」を参照）。

## 実行方法

リポジトリのルートで以下を実行してください:

```bash
bash /path/to/pr-done/scripts/sync_and_cleanup.sh
```

Claude Codeなど、このスキルのディレクトリがそのまま使える環境では、`scripts/sync_and_cleanup.sh` をそのまま実行すればOKです。

## バックマージモード（develop → main のPRをマージした後）

リリースPR（develop → main）がマージされると、mainにだけマージコミットが増え、developはmainより遅れた状態になります。そこで、developは削除せず残したまま、mainの内容をdevelopに取り込みます。

```bash
bash /path/to/pr-done/scripts/sync_and_cleanup.sh --back-merge
```

スクリプトは次の順に処理します:

1. 未コミットの変更がないか確認する（あれば中断）
2. `main` に切り替えて `origin/main` を `git pull`
3. `develop` に切り替えて `origin/develop` を `git pull`
4. `main` を `develop` にマージする（バックマージ）。developが既にmainの内容を含んでいれば、マージはせずその旨を表示する
5. `develop` を `origin/develop` に `git push` する（強制pushはしない）
6. 終了時はローカルの `develop` にいる状態になる

このモードでは **ブランチの削除は一切行いません**（developはもちろん、他のブランチも消さない）。バックマージ後の `develop` は `origin/develop` に push されます（強制pushはしません）。

**pushが拒否された場合**（`develop` が保護ブランチでPRが必須、リモートに新しいコミットがある、など）: スクリプトはエラーで終了します。ローカルの `develop` にはバックマージ済みの状態です。Claudeは `--force` などで押し切らず、拒否された内容をそのままユーザーに伝えます（例: 保護ブランチならPR経由での反映を提案）。

**コンフリクトした場合**: スクリプトは `git merge --abort` でマージを取り消してdevelopを元の状態に戻し、コンフリクトしたファイルの一覧を表示して終了します。Claudeが勝手にコンフリクトを解消しないこと。ファイル名を伝え、ユーザーに手動でのマージを促します。

## バックログタスクの完了

ブランチの掃除が終わったら、今回マージされたPRに対応するバックログタスクがあれば `/backlog` スキルで完了にします。これはgitコマンドではなく、Claude自身が会話の文脈から判断して行うステップです。**そもそも今回のPRにバックログタスクが紐づいているかどうか自体も、文脈から判断すること**（すべてのPRにバックログタスクがあるとは限らない）。

1. **バックログタスクに紐づく作業かどうかをまず判断する**: このセッション内の直近のやり取り（`pr` スキルで作成したPRのタイトル・内容、ユーザーがそれまでに言及した内容など）を見て、今回の作業がそもそもバックログタスクに紐づくものかを判断する。
   - 会話の中でバックログタスクやチケットIDへの言及が一切なく、紐づく気配もない（例: ちょっとした修正やこのスキル自体の設定変更など）場合は、バックログタスクは無いものとして扱い、完了処理はスキップする。無理に「関係ありそうなタスク」を探しにいったり、IDを推測したりしない。
   - バックログタスクに紐づきそうな気配はあるが、確信が持てない場合（後述）はユーザーに確認する。
2. **紐づくタスクがあり、IDが1つに絞り込める場合**: 確認を挟まずに `/backlog <ID> を完了にする` を実行する（`/backlog` スキルを、そのIDを完了にする指示として呼び出す）。
3. **紐づくタスクがありそうだが、IDが分からない・複数候補があり絞り込めない場合**: 推測でIDを決め打ちしない。ユーザーに「どのバックログタスクを完了にすればよいか」を確認してから `/backlog` を呼び出す。
4. **バックログタスクが無いと判断した場合**: `/backlog` は呼び出さない。この場合、実行結果にもバックログについて一切触れない（詳細は下記「実行結果の伝え方」を参照）。「バックログタスクはありませんでした」のような言及も不要。
5. ブランチ削除の結果と合わせて、（バックログタスクを完了にした場合のみ）どのタスクを完了にしたか／（IDが分からず確認が必要な場合のみ）確認待ちであることを最後にまとめて報告する。バックログタスクが無いと判断した場合は、この報告自体を省略する。

## 完了後の振る舞い（続きの作業は始めない）

このスキルの仕事は、後片付け（develop の同期、マージ済みローカルブランチの削除、必要ならバックログの完了）までです。それが終わったら、**次の作業には着手せず、提案だけして止まること。**

- 会話の流れから「次はこの作業を進めるのがよさそう」という続きが見えている場合（バックログの次のタスク、PRで言及されていた残課題、直前に話していた予定の作業など）は、最後に「次は〜〜を進めます。」のように、次の作業内容を一言で提案して終える。
- **提案した作業を実際に始めない。** ブランチを切る、ファイルを編集する、コマンドで実装を進める、`/backlog` で着手状態にする、といったことは、ユーザーが「進めて」などと明確に返答するまで行わない。
- 提案はあくまで一言にとどめる。選択肢を並べたり、計画を詳しく書き出したりしない。
- 続きの作業が会話から読み取れない場合は、無理に提案をひねり出さず、後片付けの結果を報告して終わりでよい。

## 実行結果の伝え方

スクリプトの出力をそのままユーザーに見せ、以下を明確にすること:

- developが最新化されたこと
- 削除されたブランチの一覧（削除対象がなければその旨も伝える）
- バックマージモードのときは、ブランチ削除の報告の代わりに「mainをdevelopにマージし、origin/developにpushしました」（または「developは既にmainの内容を含んでいました」）と伝える。developを削除していないことをわざわざ強調する必要はない
- バックログタスクを完了にした場合のみ、そのタスクに言及する
- バックログタスクのIDが分からずユーザーに確認が必要な場合のみ、その旨を伝える
- **バックログタスクが無いと判断した場合は、バックログについて一切言及しない。**「バックログタスクはありませんでした」「スキップしました」のような補足も含め、バックログという単語自体を出さないこと（リモートブランチと同様、紐づかないPRの後処理では触れる必要のない情報のため）

- 続きの作業が見えている場合のみ、最後に「次は〜〜を進めます。」の形で提案を添えて止まる（詳細は上記「完了後の振る舞い」を参照）

**リモートブランチの削除有無には言及しない。** このチームではPRマージ時にリモートブランチが自動削除されるか、意図的に残す運用のため、「リモートブランチは削除していません」のような補足は不要な情報であり、報告に含めないこと。

## 注意点・エッジケース

- **未コミットの変更がある場合**: スクリプトはエラーで中断します。ユーザーにコミットまたは `git stash` を促してください。
- **developブランチがローカルに存在しない場合**: エラーで中断します。`git fetch && git checkout -b develop origin/develop` などでローカルにdevelopを作る必要がある旨を伝えてください。
- **リモートブランチについて**: このスキルはローカルブランチのみを対象とし、リモート（`origin`）のブランチは一切操作しません。これはチームの運用（PRマージ時の自動削除、またはブランチを残す方針）を前提とした意図的な仕様であり、エッジケースではありません。実行結果でもこの点には触れないでください（上記「実行結果の伝え方」を参照）。
- **バックマージモードの前提**: 本流ブランチは `main`（なければ `master`）を想定しています。ローカルにどちらも無い場合はエラーで中断します。リリースPRでバックログタスクが紐づくことは通常ないので、バックログの判断は他のPRと同じく会話の文脈に従い、紐づく気配がなければ何も言及しないこと。
- **develop/main/masterという名前以外の保護ブランチがある場合**（例: `staging`）: `scripts/sync_and_cleanup.sh` 内の `PROTECTED_BRANCHES` にブランチ名を追加してください。
- **そもそもバックログタスクに紐づくPRかどうか不明な場合**: 「バックログタスクがある前提」で動かない。紐づきが読み取れなければタスクなしとして扱ってよい。この場合は`/backlog`を呼び出さないだけでなく、実行結果でもバックログについて一切言及しないこと。
- **バックログタスクIDが会話中から特定できない場合（紐づきはありそうだがIDが不明）**: 憶測でタスクを完了にしない。必ずユーザーに確認する。
- **`/backlog` スキル自体が呼び出せない・存在しない場合**: エラーをそのままユーザーに伝え、手動での完了操作を促す。
