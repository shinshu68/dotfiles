# プロジェクト初期化 (CLAUDE.md / docs/plan.md / docs/roadmap.md の作成)

デスクトップ版 Claude のチャットから呼び出す前提のスキル。ローカルの `~/.claude/CLAUDE.md` は読めないため、同じ内容を GitHub の公開リポジトリから取得して使う。生成したファイルはダウンロードしてもらい、ユーザーがプロジェクトに配置する。

## 手順

### 1. グローバル CLAUDE.md を取得する

次の2つの URL から取得する。1つ目は Claude 専用の部分で、2つ目は Claude と Codex の共通の指示。1つ目の中の `@../agents/common.md` の行の位置に2つ目の中身を展開し、1つのグローバル CLAUDE.md として扱う。

```
https://raw.githubusercontent.com/shinshu68/dotfiles/refs/heads/main/claude/CLAUDE.md
```

```
https://raw.githubusercontent.com/shinshu68/dotfiles/refs/heads/main/agents/common.md
```

- bash の `curl -sS -w "%{http_code}"` で取得し、HTTP 200 であることを確認する
- 失敗した場合は web_fetch で同じ URL を試す
- どちらか一方でも取得できなければ、取得できなかった旨を伝え、取れなかったファイルの内容を貼り付けてもらうよう依頼して止まる。推測で中身を補わない

取得した内容は「プロジェクトでも常に読み込まれる前提のルール」として扱う。

### 2. プロジェクトの情報を集める

会話・添付ファイル (README、既存コード、要件メモなど) からわかることを先に整理し、足りないものだけを質問する。一度に聞きすぎず、重要なものから聞く。

集めたい情報：

- プロジェクトの目的・背景 (何を解決するか、誰が使うか)
- スコープ (やること／やらないこと、最初のゴール)
- 技術スタック (言語、フレームワーク、主要ライブラリ、実行環境)
- ディレクトリ構成の想定 (モノレポ構成かどうか、モノレポならどのパッケージ・アプリをどのフォルダに置くか)
- ビルド・テスト・実行・lint のコマンド (決まっていれば)
- プロジェクト固有のルールや制約 (命名規則、外部 API、データの扱いなど)
- 進め方 (マイルストーン、優先順位)
- GUI のあるアプリ (モバイル・デスクトップ・Web の画面があるもの) のときだけ、見た目について次の3点。CLI・ライブラリ・サーバーだけのプロジェクトでは聞かない
  - ダークモードに対応するか (対応する場合、端末の設定に従うか、アプリ内で切り替えるか)
  - 見た目がアプリの売りかどうか (売りなら、作り込みの度合いやロードマップでの扱いにも関わる)
  - 具体的なカラーテーマが決まっているか (決まっていれば色の値やモチーフ)

決まっていない項目は無理に埋めず、plan.md の「未決事項」に回す。ユーザーが言っていない色やテーマを決定事項として書かない。

#### 選択肢を出して質問するとき

技術スタックや構成など、ユーザーに選んでもらう形で質問するときは、**選択肢を出す前に、本文で各選択肢の説明を出力する**。選択肢の名前だけを並べても、ユーザーは何を基準に選べばよいかわからないため。

各選択肢について、次の内容を書く：

- どういうものか (1〜2行の概要)
- その選択肢を挙げた根拠 (会話や添付から読み取れた要件・制約とどう結びつくか)
- 長所
- 短所・注意点 (学習コスト、運用の手間、将来の制約など)

書き方の目安：

- 選択肢ごとに見出しか太字で区切り、長所・短所は箇条書きにして比較しやすくする
- おすすめがある場合は、説明の最後に「おすすめ：〇〇 (理由)」と一言添える。ただし決めるのはユーザー
- 説明を出し終えてから、選ぶ操作だけを AskUserQuestion の選択肢 UI で出す (使えない環境では番号付きの選択肢を本文で示す)。UI の各選択肢には短いラベルだけを付け、詳細は本文の説明に任せる
- 複数の項目を一度に聞く場合も、項目ごとに「説明 → 選択」の順を崩さない

### 3. CLAUDE.md を作成する

方針：**グローバル CLAUDE.md との差分だけを書く**。グローバルはプロジェクトでも常に読み込まれるため、言語設定・Git 運用・秘匿情報の扱いなど、グローバルにある内容を書き写さない。

構成の目安：

```markdown
# <プロジェクト名>

<1〜2行の概要>

開発方針・スコープ・設計の詳細は docs/plan.md を参照する。
(分割した場合は「docs/plan.md を起点に、docs/ 配下の各ドキュメントを参照する」とする)

## 技術スタック
## ディレクトリ構成
## コマンド
(ビルド・テスト・実行・lint。1コマンドずつコードブロックで)
## 動作確認
(何をどの手段で確かめるか、使わない手段とその理由、ユーザーに頼むときの手順)
## プロジェクト固有のルール
```

「動作確認」の節には、次の内容を書く：

- 何をどの手段で確かめるか (自動テスト、ローカル実行、エミュレーター、ユーザーに頼む確認など)。確認に使う環境 (AVD 名など) を1つに決めて書く
- 使わない手段とその理由 (例：実機の adb 操作は使わない、など)
- ユーザーに頼むときの手順と、具体的に確かめてほしい点

グローバルの CLAUDE.md には動作確認の進め方 (自分で確かめられる範囲を先に自分で行い、ユーザーに頼むのはそれでは確かめられない部分だけにする、など) がすでにある。その一般的なルールは書き写さず、このプロジェクトでの具体的な手段・環境・手順だけを書く。

- グローバルと異なる運用をするとき (例：このプロジェクトは develop を使わない) だけ、「グローバルの〇〇より優先する」と明記して書く
- 決まっていないセクションは見出しごと省くか、「未定 (docs/plan.md の未決事項を参照)」とする
- 簡潔に保つ。CLAUDE.md は毎回読み込まれるため、説明的な文章や背景は plan.md に寄せる

#### モノレポ構成の場合

1つのリポジトリに複数のアプリ・パッケージ (例：モバイルアプリとサーバー、フロントエンドとバックエンドと共通ライブラリ) を置く構成なら、ルートの CLAUDE.md に加えて、**各パッケージのフォルダにもそれぞれ CLAUDE.md を作る**。

モノレポかどうかは、会話や添付から判断する。複数のアプリ・パッケージが出てくるのに1つのリポジトリにまとめるかどうかがわからないときは、「選択肢を出して質問するとき」のルールに従って、モノレポにする場合と別々のリポジトリにする場合の長所・短所を説明してから確認する。

Claude Code は、起動したディレクトリとその上の階層の CLAUDE.md を最初に読み込み、下の階層の CLAUDE.md はそのフォルダのファイルを扱うときに読み込む。この仕組みに合わせて、書く場所を次のように分担する。

**ルートの CLAUDE.md** (リポジトリ全体に関わることだけ)：

- プロジェクト全体の概要と、docs/ への参照
- パッケージの一覧 (フォルダのパスと、それぞれの役割を一言ずつ)
- パッケージをまたぐルール (パッケージ間の依存の向き、共通の型・API 定義の置き場所、共通の命名規則など)
  - パッケージ間の仕様 (API・通信の取り決めなど) は1つのファイルに置き、そのファイルを唯一の正と明記する
  - 仕様を変えるときの順序 (仕様 → 提供側 → 利用側) を書く
  - 仕様の更新は、実装より先のコミットにすることを書く
  - 実装の修正でタイムアウトや再試行などの振る舞いが変わるときは、その修正と同じコミットで仕様も直すことを書く
- リポジトリ全体に対するコマンド (ワークスペース全体のビルド・テストなど。あれば)
- 動作確認のうち、全パッケージに共通する部分 (確認の手段がすべてのパッケージで同じならその内容、ユーザーに頼むときの共通の流れなど。あれば)

**各パッケージの CLAUDE.md** (`<パッケージのフォルダ>/CLAUDE.md`)：

- そのパッケージの役割 (1〜2行)
- そのパッケージの技術スタック
- そのパッケージ内のディレクトリ構成
- そのパッケージのコマンド (どのディレクトリで実行するかがわかるように書く)
- そのパッケージの動作確認 (確認の手段・環境がパッケージごとに違う場合に、そのパッケージでの手段・環境・手順。共通の部分はルートに書き、ここには差分だけを書く)
- そのパッケージ固有のルール

守ること：

- ルートに書いた内容を各パッケージの CLAUDE.md に書き写さない。グローバルとルートの関係と同じく、各パッケージには差分だけを書く
- 他のパッケージに関わる内容 (API の呼び出し方など) は、提供する側のパッケージか、ルートの「パッケージをまたぐルール」に1か所だけ書く
- 開発方針のドキュメントは、パッケージごとに分けずリポジトリルートの docs/ にまとめる。パッケージ固有の設計が多いときは、手順4の分割ルールに従って docs/ 配下にパッケージ単位のファイルを作ってもよい。各パッケージの CLAUDE.md からは「リポジトリルートの docs/xxx.md」の形で参照する
- 中身がほとんどない CLAUDE.md は作らない。パッケージ固有の情報がまだほとんど決まっていない場合は、そのパッケージの CLAUDE.md は作らず、ルートのパッケージ一覧に役割だけを書いておく

### 4. docs/plan.md と docs/roadmap.md を作成する

どちらも人が読むためのドキュメント。plan.md には開発方針を、roadmap.md にはマイルストーンと各完了条件を書く。

plan.md の構成の目安：

```markdown
# <プロジェクト名> 開発方針

## 目的・背景
## スコープ
### やること
### やらないこと
## 技術選定
(選んだ技術と、選んだ理由)
## 設計方針
(アーキテクチャ、データの流れ、主要なモジュールの役割など)
### 見た目
(GUI のあるアプリのときだけ。ダークモード、見た目が売りか、カラーテーマ)
## 進め方
(「マイルストーンと各完了条件は docs/roadmap.md を参照」のように、リンクと一言の説明だけ)
## 未決事項
```

- ロードマップ (マイルストーンと完了条件) は、規模にかかわらず `docs/roadmap.md` に書く。書き方は下の「docs/roadmap.md を作成する」に従う
- 「見た目」には、手順2で聞いた3点の答えを書く。決まっていない項目は未決事項に回す。分割して `docs/ui.md` など画面・UI のファイルがある場合はそちらに書き、plan.md からリンクで辿れるようにする (icon-create スキルが CLAUDE.md・docs/plan.md・テーマ色の定義からアイコンの色の候補を読み取るため)
- 技術選定には理由を添える (後から見直すときの判断材料になるため)
- 方式を決めたら、その判断を書いた項目のすぐ下に「〜する方法は、…のため採用していない」と、選ばなかった案と理由を書く。同じ案の再検討を防ぎ、元に戻すと不具合が再発する方式を設計の資料からも判断できるようにするため
  - 技術選定だけでなく、設計全般の判断が対象。技術選定の判断は「技術選定」の該当項目の下に、設計の判断は「設計方針」の該当項目の下に書く
  - 実装前に決めた案に加えて、不具合の修正で選んだ方式も、あとから同じ形で追記していく運用にする。plan.md にもその旨を一言書いておく
  - docs/ を分割して `docs/architecture.md` などがある場合は、判断の内容を書いたそのファイルの該当項目の下に書く
- ユーザーが言っていないことを決定事項として書かない。提案する場合は「案」と明記するか、未決事項に入れる

#### docs/roadmap.md を作成する

マイルストーンごとに「実施すること」と「完了条件」を並べる。着手するときと main へマージする前に、何を確かめればよいかが1か所でわかるようにするため。ロードマップは進めながら何度も更新するので、plan.md とは分けておく。

ひな形：

```markdown
# <プロジェクト名> ロードマップ

## 進め方

- マイルストーンは develop から main へマージする単位にする。層ごと (DB だけ、画面だけなど) ではなく、薄くても端から端まで動かして確認できる単位で区切る
- 完了条件をすべて満たしたら、リリース前のコードレビューを経て main へマージする
- 完了条件の確認の手段 (自動テスト、エミュレーター、ユーザーに頼む実機の確認など。詳細は CLAUDE.md の「動作確認」)
- 順番と区切りは案。進めながら見直す

## M1: <マイルストーン名>

<このマイルストーンで到達する状態を一文で>

着手前に、<未決事項のうち、このマイルストーンの前に決めるもの> を決める。(あれば)

### 実施すること

- <実施すること>
- <実施すること>

### 完了条件

- [ ] <外から見て確かめられる振る舞い>
- [ ] <テストで確かめること>
- [ ] 実機: <ユーザーに頼む確認>

## M2: ...
```

完了条件の書き方：

- 「○○を実装した」ではなく、操作と結果で書く (例：「誤った URL で疎通確認すると、失敗したことが画面に出る」)
- 正常系だけでなく、失敗・空・境界の場合も入れる (例：0 件のとき、サーバーが止まっているとき、送信に失敗したとき)
- テストで確かめる項目は「〜をテストで確かめている」「〜のテストが通る」と書く
- ユーザーに頼む確認は、先頭に `実機:` のように手段を付けて区別する
- 「進め方」の確認の手段は、CLAUDE.md の「動作確認」を参照する形にして、内容を重ねて書かない

そのほか：

- 着手前に決める未決事項があるマイルストーンは、概要の一文の直後に「着手前に、○○を決める」と書く
- 他のシステムの予定改修など、マイルストーンの外の依存があれば、末尾に節を設けて表で示す
- 見た目がアプリの売りの場合は、見た目を詰める時期 (専用のマイルストーンにするか、各マイルストーンの完了条件に含めるか) も検討する。ユーザーに選んでもらうときは「選択肢を出して質問するとき」のルールに従う

#### 規模が大きいときは複数ファイルへの分割を検討する

書き始める前に、1つの plan.md に収まる規模かを判断する。次のどれかに当てはまるなら、分割を検討する。

- 機能が多く、機能ごとに仕様や画面・入出力の説明が必要になる
- 構成要素 (フロントエンド／バックエンド／外部サービス連携など) が複数あり、構成の説明が長くなる
- まとめると plan.md がおおむね 300 行を超えそう

**どのファイルに分けるかは、そのプロジェクトの内容から決める**。決まった型に当てはめるのではなく、そのプロジェクトで分量が多くなるテーマ、独立して読み返されそうなテーマを、それぞれ1ファイルにする。

`plan.md` と `roadmap.md` は分割するかどうかにかかわらず常に作る。それ以外のファイルについて、参考までに分割の一例を示す。これはあくまで一例で、この2つをそろえる必要も、この名前を使う必要もない。

```
docs/
├── plan.md          # 概要と目次 (分割しても必ず残す)
├── roadmap.md       # 常に作る：マイルストーンと各完了条件
├── feature.md       # 例：機能ごとの仕様・振る舞い
└── architecture.md  # 例：アーキテクチャ、データの流れ、主要モジュールの役割
```

プロジェクトによっては、ほかにも次のような単位が考えられる (これも例であり、網羅ではない)：

- データモデル・DB スキーマ (`data-model.md` など)
- 外部 API・外部サービスとの連携仕様 (`api.md`、`integrations.md` など)
- 画面・UI の設計 (`ui.md` など)
- テスト方針 (`testing.md` など)
- デプロイ・運用 (`deployment.md`、`operations.md` など)
- 機能が特に多い場合の機能ごとのファイル (`docs/features/<機能名>.md` など)

逆に、分けるほどの分量がないテーマは無理に別ファイルにせず、plan.md に残す。

守ること：

- 分割しても `docs/plan.md` は概要と目次として残す。目的・背景、スコープ、未決事項など全体に関わる内容と、各ファイルへのリンク (各ファイルに何が書いてあるかの一言説明つき。roadmap.md も含める) を置く。CLAUDE.md からの参照先や、他のスキル (repo-create など) が `docs/plan.md` を前提にしているため
- 同じ内容を複数のファイルに書かない。詳細は1か所に置き、他のファイルからはリンクで参照する
- 分割するかどうか、どう分けるかは、生成前にユーザーに確認する。その際は「選択肢を出して質問するとき」のルールに従い、「plan.md と roadmap.md の2つにまとめる」「さらに分割する (提案するファイル構成)」それぞれの長所・短所を説明してから選んでもらう
- 規模が小さく分割するほどではない場合は、確認せずに plan.md と roadmap.md の2つで作る

### 5. ファイルを渡す

- `/mnt/user-data/outputs/CLAUDE.md` と `/mnt/user-data/outputs/docs/` 配下 (plan.md・roadmap.md と、分割した場合はその他のファイル) に Markdown ファイルとして書き出し、present_files でまとめて渡す
- モノレポの場合は、各パッケージの CLAUDE.md をリポジトリと同じフォルダ構成で `/mnt/user-data/outputs/<パッケージのフォルダ>/CLAUDE.md` に書き出し、一緒に渡す
- Claude Docs や公開ページ (Artifact) にはしない。ローカルのリポジトリに置くファイルなので、素の Markdown ファイルで渡す
- 渡した後は、内容の要点を2〜3行で伝えるにとどめ、配置場所 (プロジェクトのルートに CLAUDE.md、docs/ にそれ以外、モノレポなら各パッケージのフォルダにそれぞれの CLAUDE.md) を一言添える

## 修正を頼まれたとき
