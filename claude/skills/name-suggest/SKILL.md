# name-suggest

プロジェクト・アプリの名前を、ヒアリング → 候補提示 → 反応を受けて出し直す、という往復で一緒に決めていくスキル。

名前は好みの比重が大きく、一度で決まることはまれ。最初の候補は「方向性を探るための叩き台」と考え、ユーザーの反応から好みを読み取って絞り込んでいく。往復は会話の中で続ける (ファイルには記録しない)。

## 1. 分かっていることを先に拾う

このスキルは、概要だけ決まっていて CLAUDE.md や docs/plan.md はまだない段階で使う想定。決めた名前を project-init に渡し、その名前で CLAUDE.md・plan.md を作る流れになる。仮の名前でドキュメントを先に作ると、決まったあとの書き換えや書き換え漏れが出るため、名前を先に決める。

ヒアリングの前に、会話で伝えられた概要から分かること (何をするものか・誰が使うか・対象プラットフォームなど) を拾う。概要は一言でも、メモの貼り付けでもよい。すでに分かっている項目は聞き直さない。同じことを答えさせるのはユーザーの手間になるため。

## 2. まとめてヒアリングする

足りない情報を一度にまとめて聞く。往復を減らすため、少しずつ聞くことはしない。

**何を作るのかが分からない場合**は、選択肢では答えられないので、まず本文で「どんなものを作るのか (何をするもの・誰が使うか)」を尋ねて止まる。概要のメモがあればそのまま貼ってよいことも添える。

**概要が分かったら**、次の項目を AskUserQuestion の質問カード (最大4問) で聞く。どれも「Other」で自由に答えられる。

- 言語・スタイル: 英語 / 日本語 (ローマ字) / 造語 / こだわらない
- 雰囲気: シンプル・機能が伝わる / 親しみやすい・遊び心 / かっこいい・洗練 / こだわらない
- 長さ: 短い (1語・〜8文字程度) / 2語程度まで / こだわらない
- 公開範囲: 個人用 / ストア・GitHub などで公開予定

カードで聞けない条件 (入れたい単語・避けたい単語や響き・参考にしたい好きな名前など) は、カードと同じ応答の本文で「あれば一緒に教えてください」と添える。返答で触れられなければ「特になし」と扱ってよい。ここは任意項目として最初から示しているため。

## 3. 候補を出す

候補は1回に5つ程度。毎回の応答の冒頭に、ここまでに分かった条件を短くまとめる (例:「条件: 英語・短め・シンプル / 避ける: 〜Hub」)。会話が長くなっても条件を見失わないようにするため、またユーザーが条件の読み違いに気づけるようにするため。

候補は方向性をばらして出す。最初のうちは好みが分からないので、似た名前ばかりだと反応から得られる情報が少ない。例えば次のような方向を混ぜる。

- 機能をそのまま表す (例: 動画を流す → stream 系)
- 比喩・連想 (機能から連想される物や情景)
- 造語・組み合わせ (2語を縮める、語尾を変える)
- 略語・頭字語

各候補は次の形で書く。

```
### 1. Fluvio
- 読み: フルヴィオ
- 由来: ラテン語の fluvius (川) から。動画が途切れず流れるイメージ
- リポジトリ名: fluvio
```

- 読みは、英語やカタカナ表記から読み方が一つに決まらないときに付ける
- 由来・理由は、なぜこの名前がこのプロジェクトに合うのかまで書く。語源だけでは選ぶ判断材料にならないため
- リポジトリ名は小文字・ハイフン区切り (kebab-case) にしたときの表記。表示名と同じなら省いてよい
- 有名なプロダクトと同じ・紛らわしい名前は、自分で気づける範囲で最初から外す

候補のあとに、反応の返し方を短く添える (例:「気に入ったもの・違うもの・惜しいものがあれば教えてください。理由も一言あると次の候補に活かせます」)。

## 4. 反応を受けて出し直す

ユーザーの反応から好みを読み取り、次の候補に反映する。

- 気に入った候補があれば、その方向 (語感・由来の付け方・長さ) を広げた候補を出す
- 違うと言われた候補の方向は外す。理由が添えられていれば、それを条件に加える
- 「全部違う」と言われたら、何が違ったのかを推測で決めずに聞く。方向性そのものを読み違えている可能性が高いため
- 気に入った候補は、次の回で消さずに残しておく (比較できるように)

新しく分かった条件は、次の応答冒頭の条件まとめに反映する。

## 5. 有力候補の重複を確かめる

候補が2〜3個に絞られたとき、またはユーザーが確認を頼んだときに、その候補だけ WebSearch で既存の同名プロダクトがないか確かめる。全候補を毎回調べると応答が重くなり、まだ方向性を探っている段階の候補は調べても無駄になりやすいため。

それまでの間、気に入った候補が出た回では、応答の最後に「気になる候補があれば重複を確認します」と一言添える。

公開範囲や対象プラットフォームに合わせて、次のような場所を見る。

- GitHub の同名リポジトリ (特に同じ分野のもの)
- アプリなら Google Play / App Store の同名アプリ
- ライブラリ・CLI なら npm・PyPI・crates.io など該当するパッケージレジストリ
- 同じ分野の有名なサービス・製品

結果は候補ごとに「同名・類似の例 (分野)」を事実として短く報告する。同じ分野に有名なものがあれば、その旨をはっきり伝える。商標上問題ないかの判断はしない (法的な判断になるため)。公開予定で気になる場合は、商標の検索サービスで確認できることを一言添える程度にとどめる。個人用のプロジェクトなら、かぶっていても困らないことが多いので、その点も踏まえて伝える。

## 6. 決まったら

ユーザーが名前を決めたら、そのまま project-init に渡せる形でまとめて示す。

```
## 決定した名前
- プロジェクト名 (表示名): Fluvio
- リポジトリ名・ディレクトリ名: fluvio
- 概要: Windows の外付け HDD の動画を、LAN 内の Android 端末からストリーミング再生するアプリ
- 由来: ラテン語の fluvius (川) から。動画が途切れず流れるイメージ
```

- 概要は、ヒアリングで分かった内容を一文にまとめる
- パッケージ名やアプリ ID (例: Android の applicationId、Go のモジュール名) が必要になりそうなら、例を一行添える

まとめのあとに「この名前で project-init に進めます」と案内して止まる。project-init の実行やディレクトリの作成はこのスキルでは行わず、ユーザーの指示を待つ。
