# PR作成 (/pr)

現在の作業ブランチと、指定したベースブランチとの差分から、GitHubのプルリクエストを自動作成するスキル。

## ベースブランチの決め方

ユーザーの入力に `/pr <ブランチ名>` のように引数が付いていれば、そのブランチをベースブランチとして使う(例: `/pr main` → `main`、`/pr master` → `master`)。引数がなく単に `/pr` やPR作成の依頼だけの場合は `develop` をデフォルトのベースブランチとする。

## 前提条件

- カレントディレクトリがGitリポジトリであること
- `gh` CLIがインストール・認証済みであること
- リモート `origin` に、上記で決めたベースブランチが存在すること
これらが満たされていない場合、`scripts/check_status.sh` がエラーメッセージを出して停止するので、その内容をそのままユーザーに伝える(例: `gh auth login` を促す、など)。

## 手順

### 0. コードレビューを先に行う

ベースブランチが `develop`(作業ブランチのPR)と `main` / `master`(develop からのリリースPR)のときに行う。それ以外のベースブランチではこのステップを飛ばす。

PRの種類ごとの違い:

| | 作業ブランチのPR | リリースPR |
|---|---|---|
| 先端(レビューする側のコミット) | `HEAD` | `origin/develop` |
| effort | `medium`。了承を取らずに実行する | 差分の規模を見て提案し(基本は `high`、変更量が大きいと判断したら `xhigh`。`max` は使用制限に達するため提案しない)、ユーザーの了承を得てから実行する |
| 記録のファイル名 | `feature-review-<ブランチ名>.md`(ブランチ名の `/` は `-` に置き換える) | `release-review.md` |

最初のレビューの後に指摘への修正が入ったら、前回レビューしたコミットからの差分だけを再びレビューする(修正の変更がレビューされずに develop や main へ入らないようにするため)。レビューした範囲と指摘ごとの判断は自動メモリに記録し、/clear 後や別のセッションでも共有する(後述の「レビュー済みの記録」)。そのため、まず `git fetch origin` でリモートを最新化してから、記録を確認する:

- 記録がない: 最初のレビューをする。対象は `origin/<ベースブランチ>...<先端>`
- 記録の「レビュー済みのコミット」が今の先端と同じ: レビュー後に変更がないので、このステップを飛ばしてステップ1に進む
- 記録の「レビュー済みのコミット」より先端が進んでいる: 再レビューをする。対象は `<レビュー済みのコミット>...<先端>`
- 記録の「レビュー済みのコミット」が先端の祖先でない(rebase したときなど): 再レビューの範囲を決められないので、「記録がない」場合と同じ対象でレビューする。「判断済みの指摘」は引き継ぐ

対象が決まったら、`git diff --name-only <対象>` で変更ファイルを確かめる。全てドキュメント(`*.md` と `docs/` 配下)なら、レビューせず、記録も書かずにステップ1に進む。

レビューの実行手順:

1. Codex CLI の `codex review` でレビューする(後述の「Codex でのレビュー」)。Codex が使えないときは code-review スキルに切り替え、切り替えたことと理由をユーザーに伝える
   - code-review スキルは、effort と対象を明示して呼び出す(effort を省略すると前回のレベルが使われるため、必ず指定する。例: `medium origin/develop...HEAD`、`high origin/main...origin/develop`、`high a1b2c3d...origin/develop`)
   - 範囲指定が受け付けられなかった場合は、対象を先端のブランチ(作業ブランチのPRでは今のブランチ、リリースPRでは `develop`)にして呼び出し直す。再レビューのときは、その結果から対象の範囲の差分に含まれない指摘を除く
2. レビューを実行したら、すぐに記録の「レビュー済みのコミット」を今の先端のハッシュに更新する(後述)
3. 再レビューのときは、記録の「判断済みの指摘」と照らし合わせる。「問題ない」「対応しない」と決めた指摘と同じものは、修正で前提が大きく変わっていない限り対応しない項目として扱い、結果の末尾に判断済みとして短くまとめる。前提が変わったと判断したものだけ、何が変わったかを添えて改めて挙げる
4. レビュー結果を日本語で出力し、各指摘に対応すべきかを判断して添える
5. 対応すべき項目の扱いをユーザーに確認する。作業ブランチのPRでは、今のブランチで直すか backlog スキルでバックログに積むかを確認する。リリースPRでは、全てバックログに積むかを確認する。ユーザーの返答で各指摘の扱いが決まったら、記録の「判断済みの指摘」に追記する
6. 作業ブランチのPRで、対応すべき指摘がなければステップ1に進む。それ以外は、ここでPRの作成には進まずに止まる。指摘への修正を先にするか、このままPRを出すかはユーザーが決める。リリースPRの修正は develop から切ったブランチで行う。改めてPR作成を指示されたら、ステップ0の最初から進める(修正が入っていれば再レビューになる)

#### Codex でのレビュー

Codex は指摘を出すだけで、各指摘の判断・記録・ユーザーへの確認は上の手順どおり Claude が行う。

プロジェクトのディレクトリから次のように実行する。stdout にはレビュー結果(Codex の最後のメッセージ)だけが出て、実行ログは stderr に出るので、stderr は一時ファイルに逃がす:

```bash
log=$(mktemp)
codex review \
  -c model_reasoning_effort=<effort> \
  -c sandbox_mode=read-only \
  -c approval_policy=never \
  "<指示文>" 2>"$log"
echo "exit=$?"
```

- `<effort>` は上の表の effort(`medium` / `high` / `xhigh`)
- `--base`・`--commit`・`--uncommitted` は指示文と併用できない(codex-cli 0.167 で確認)ため、範囲は指示文に書く
- 指示文には対象の範囲を書く。例: 「`origin/develop...HEAD` の差分をレビューしてください。」。リリースPRでは「各機能は個別にレビュー済みなので、機能間の整合性と全体の設計を重点的に見てください。」を添える。日本語での出力やレビューだけにする役割は、グローバルの AGENTS.md に書いてあるので指示文には書かない
- effort が高いと時間がかかり、Bash の実行時間の上限(10分)を超えることがあるため、`run_in_background` で実行し、終了の通知を待つ
- 再レビューのときは、結果から対象の範囲の差分に含まれない指摘を除く
- 終わったら一時ファイルを消す

次のときは Codex が使えないとみなし、code-review スキルに切り替える。理由は stderr の末尾(`tail -n 20 "$log"`)から読み取って伝える:

- `codex` コマンドがない(`command -v codex` で確かめる)
- 終了コードが 0 以外(使用量の上限、認証切れ、ネットワークのエラーなど)
- 終了コードが 0 でも stdout が空

#### レビュー済みの記録

保存先は Claude Code の自動メモリのディレクトリ(システムプロンプトで案内されている memory ディレクトリ。通常は `~/.claude/projects/<プロジェクト>/memory/`)。

1. 上の表のファイルに次の内容を書く。再レビューのときは、「レビュー済みのコミット」を上書きし、「レビューの履歴」と「判断済みの指摘」に追記する(前回までの内容は消さない)
   - レビュー済みのコミット: 最後にレビューした時点の先端のコミットハッシュ
   - レビューの履歴: 回ごとの日付・対象の範囲・effort・レビューした手段(Codex / code-review)
   - 判断済みの指摘: 指摘ごとに、ファイルと内容の要約・判断(対応する / 対応しない / 問題ない)・理由
2. `MEMORY.md`(索引)に次のどちらかの1行を追加する(既に同じ行があれば重複させない):

   ```
   - [リリース前レビュー済み](release-review.md) — 一時メモ。/pr でリリースPRを作成したら削除する
   - [<ブランチ名> のレビュー済み](feature-review-<ブランチ名>.md) — 一時メモ。/pr でPRを作成したら削除する
   ```

**自動メモリが使えない場合**(システムプロンプトに memory ディレクトリの案内がない、autoMemoryEnabled が false など)は、`~/.claude/release-review/<リポジトリ名>.md`(作業ブランチのPRでは `~/.claude/release-review/<リポジトリ名>-<ブランチ名>.md`)に同じ内容で保存する(索引への追記はしない)。ステップ0でレビュー済みかを確認するときは、こちらも見る。

記録の削除はステップ3でPRを作成できたときに行う。

### 1. 状態確認スクリプトを実行する

第1引数にベースブランチ名を渡す(省略時は `develop`):

```bash
bash scripts/check_status.sh <ベースブランチ名>
# 例: bash scripts/check_status.sh main
# 引数を省略した場合は develop が使われる
```

このスクリプトが一括でやってくれること:

1. Gitリポジトリかどうか、`gh`が使えるかどうかを確認
2. 現在のブランチ名を取得(指定したベースブランチ自身の場合はエラーで停止)
3. `git fetch origin <ベースブランチ>` でベースブランチを最新化
4. 未コミットの変更があれば件数を警告として表示する(ただし処理は続行。**未コミットの変更はPRの対象に含めない** — コミット済みの差分のみが対象)
5. ベースブランチとのマージベースを起点に、コミット一覧・変更ファイル一覧・diff本文を出力
6. 差分となるコミットが1つもなければ `INFO: 差分がありません` と出して終了(この場合PRは作らずユーザーにそのまま伝える)
7. 同じブランチ・ベースで既存のPRがあれば `EXISTING_PR: <url>` を出して終了(この場合は新規作成せず、既存PRのURLをユーザーに案内する)
8. ローカルブランチがリモートにpushされていない、またはリモートより進んでいる場合は **自動で** `git push -u origin <branch>` する
9. 最後に `READY_FOR_PR` と表示されたら、PR作成に進んでよい合図

### 2. PRのタイトルと本文を日本語で作成する

スクリプトの出力(コミット一覧・変更ファイル一覧・diff)を読んで、以下を**自分の言葉で**組み立てる。コミットメッセージやdiffをそのまま貼り付けるのではなく、変更の意図を汲み取って要約すること。

- **タイトル**: 変更内容全体を1行で要約した日本語の文。「〇〇を修正」「〇〇機能を追加」のように、何をしたかが一目でわかるように書く。
- **本文**: 変更点を箇条書きでまとめる。ファイル単位ではなく、意味のある変更のまとまり単位で書く(例: 「バリデーション処理を追加」「不要になった旧APIの呼び出しを削除」など)。細かすぎる差分の羅列にせず、レビュアーが要点を掴めるようにする。

本文の例:

```markdown
## 概要
ユーザー登録時のメールアドレス重複チェックを追加した。

## 変更点
- 登録APIにメールアドレスの重複チェックを追加
- 重複時に409エラーを返すように変更
- 対応するユニットテストを追加
```

### 3. PRを作成する

本文に改行や記号を含むため、ヒアドキュメントで渡す(直接 `--body` にベタ書きするとシェルのクォート崩れの原因になるため避ける):

```bash
gh pr create --base "<ベースブランチ名>" --title "<タイトル>" --body "$(cat <<'EOF'
<本文(Markdown)>
EOF
)"
```

- 常に通常のPRとして作成する(`--draft` は付けない)
- ステップ1で `EXISTING_PR:` が出ていた場合はこのコマンドは実行せず、そのURLを案内する
- 本文はステップ2で作成した内容のみとする。`🤖 Generated with [Claude Code]` のような定型の帰属(attribution)表記は追加しない(これを完全に止めるには `.claude/settings.json` 等で `attribution.pr` を空文字に設定するのが確実)

PRを作成できたら、そのPRのレビュー済みの記録(記録のファイルと `MEMORY.md` の索引の行、または `~/.claude/release-review/` の下のファイル)があれば削除する。PRの作成に失敗した場合や、`EXISTING_PR:` で新規作成しなかった場合は削除しない。

### 4. 結果をユーザーに伝える

`gh pr create` の出力にPRのURLが含まれるので、それをそのまま提示する。レビュー済みの記録を削除した場合は、そのことも伝える。

## エッジケースの扱い

| 状況 | 対応 |
|---|---|
| `gh` 未インストール/未認証 | インストールや `gh auth login` を促して停止 |
| Gitリポジトリでない | エラーを伝えて停止 |
| リモートに指定したベースブランチがない | エラーを伝えて停止 |
| 現在のブランチが指定したベースブランチ自身 | 作業ブランチへの切り替えを案内して停止 |
| ベースブランチとの差分(コミット)がゼロ | 「差分がないためPRの必要はない」旨を伝えて停止(PRは作らない) |
| 未コミットの変更がある | 警告として件数だけ伝え、コミット済みの差分のみでPRを作成する(未コミット分は無視) |
| 同じブランチで既にPRが存在する | 新規作成せず、既存PRのURLを案内する |
