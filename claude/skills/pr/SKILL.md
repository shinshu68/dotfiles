# PR作成 (/pr)

現在の作業ブランチと、指定したベースブランチとの差分から、GitHubのプルリクエストを自動作成するスキル。

## ベースブランチの決め方

ユーザーの入力に `/pr <ブランチ名>` のように引数が付いていれば、そのブランチをベースブランチとして使う(例: `/pr main` → `main`、`/pr master` → `master`)。引数がなく単に `/pr` やPR作成の依頼だけの場合は `develop` をデフォルトのベースブランチとする。

## 前提条件

- カレントディレクトリがGitリポジトリであること
- `gh` CLIがインストール・認証済みであること
- リモート `origin` に、上記で決めたベースブランチが存在すること
これらが満たされていない場合、`scripts/check_status.sh` がエラーメッセージを出して停止するので、その内容をそのままユーザーに伝える(例: `gh auth login` を促す、など)。

## 手順

### 0. リリースPRの場合はコードレビューを先に行う

ベースブランチが `main` / `master` のとき(develop からのリリースPR)だけ行う。それ以外のベースブランチではこのステップを飛ばす。

最初のレビューの後に、指摘への修正が develop に入ったら、前回レビューしたコミットからの差分だけを再びレビューする(修正の変更がレビューされずに main へ入らないようにするため)。レビューした範囲と指摘ごとの判断は自動メモリに記録し、/clear 後や別のセッションでも共有する(後述の「レビュー済みの記録」)。そのため、まず `git fetch origin` でリモートを最新化してから、記録(`release-review.md`)を確認する:

- 記録がない: 最初のレビューをする。対象は `origin/<ベースブランチ>...origin/develop`
- 記録の「レビュー済みのコミット」が今の `origin/develop` と同じ: レビュー後に変更がないので、このステップを飛ばしてステップ1に進む
- 記録の「レビュー済みのコミット」より `origin/develop` が進んでいる: 再レビューをする。対象は `<レビュー済みのコミット>...origin/develop`

どちらのレビューも、差分の規模を見て effort を提案し(基本は `high`、変更量が大きいと判断したら `xhigh`。`max` は使用制限に達するため提案しない)、ユーザーの了承を得てから実行する。

レビューの実行手順:

1. code-review スキルを、effort と対象を明示して呼び出す(effort を省略すると前回のレベルが使われるため、必ず指定する。例: `high origin/main...origin/develop`、`high a1b2c3d...origin/develop`)
   - 範囲指定が受け付けられなかった場合は、対象を `develop` にして呼び出し直す。再レビューのときは、その結果から対象の範囲の差分に含まれない指摘を除く
2. レビューを実行したら、すぐに記録の「レビュー済みのコミット」を今の `origin/develop` のハッシュに更新する(後述)
3. 再レビューのときは、記録の「判断済みの指摘」と照らし合わせる。「問題ない」「対応しない」と決めた指摘と同じものは、修正で前提が大きく変わっていない限り対応しない項目として扱い、結果の末尾に判断済みとして短くまとめる。前提が変わったと判断したものだけ、何が変わったかを添えて改めて挙げる
4. レビュー結果を日本語で出力し、各指摘に対応すべきかを判断して添える
5. 対応すべき項目を、全て backlog スキルでバックログに積むかをユーザーに確認する。ユーザーの返答で各指摘の扱いが決まったら、記録の「判断済みの指摘」に追記する
6. ここでPRの作成には進まずに止まる。指摘への修正(develop から切ったブランチで行う)を先にするか、このままリリースPRを出すかはユーザーが決める。改めてPR作成を指示されたら、ステップ0の最初から進める(修正が develop に入っていれば再レビューになる)

#### レビュー済みの記録

保存先は Claude Code の自動メモリのディレクトリ(システムプロンプトで案内されている memory ディレクトリ。通常は `~/.claude/projects/<プロジェクト>/memory/`)。

1. `release-review.md` に次の内容を書く。再レビューのときは、「レビュー済みのコミット」を上書きし、「レビューの履歴」と「判断済みの指摘」に追記する(前回までの内容は消さない)
   - レビュー済みのコミット: 最後にレビューした時点の `origin/develop` のコミットハッシュ
   - レビューの履歴: 回ごとの日付・対象の範囲・effort
   - 判断済みの指摘: 指摘ごとに、ファイルと内容の要約・判断(対応する / 対応しない / 問題ない)・理由
2. `MEMORY.md`(索引)に次の1行を追加する(既に同じ行があれば重複させない):

   ```
   - [リリース前レビュー済み](release-review.md) — 一時メモ。/pr でリリースPRを作成したら削除する
   ```

**自動メモリが使えない場合**(システムプロンプトに memory ディレクトリの案内がない、autoMemoryEnabled が false など)は、`~/.claude/release-review/<リポジトリ名>.md` に同じ内容で保存する(索引への追記はしない)。ステップ0でレビュー済みかを確認するときは、こちらも見る。

記録の削除はステップ3でリリースPRを作成できたときに行う。

### 1. 状態確認スクリプトを実行する

第1引数にベースブランチ名を渡す(省略時は `develop`):

```bash
bash scripts/check_status.sh <ベースブランチ名>
# 例: bash scripts/check_status.sh main
# 引数を省略した場合は develop が使われる
```

このスクリプトが一括でやってくれること:

1. Gitリポジトリかどうか、`gh`が使えるかどうかを確認
2. 現在のブランチ名を取得(指定したベースブランチ自身の場合はエラーで停止)
3. `git fetch origin <ベースブランチ>` でベースブランチを最新化
4. 未コミットの変更があれば件数を警告として表示する(ただし処理は続行。**未コミットの変更はPRの対象に含めない** — コミット済みの差分のみが対象)
5. ベースブランチとのマージベースを起点に、コミット一覧・変更ファイル一覧・diff本文を出力
6. 差分となるコミットが1つもなければ `INFO: 差分がありません` と出して終了(この場合PRは作らずユーザーにそのまま伝える)
7. 同じブランチ・ベースで既存のPRがあれば `EXISTING_PR: <url>` を出して終了(この場合は新規作成せず、既存PRのURLをユーザーに案内する)
8. ローカルブランチがリモートにpushされていない、またはリモートより進んでいる場合は **自動で** `git push -u origin <branch>` する
9. 最後に `READY_FOR_PR` と表示されたら、PR作成に進んでよい合図

### 2. PRのタイトルと本文を日本語で作成する

スクリプトの出力(コミット一覧・変更ファイル一覧・diff)を読んで、以下を**自分の言葉で**組み立てる。コミットメッセージやdiffをそのまま貼り付けるのではなく、変更の意図を汲み取って要約すること。

- **タイトル**: 変更内容全体を1行で要約した日本語の文。「〇〇を修正」「〇〇機能を追加」のように、何をしたかが一目でわかるように書く。
- **本文**: 変更点を箇条書きでまとめる。ファイル単位ではなく、意味のある変更のまとまり単位で書く(例: 「バリデーション処理を追加」「不要になった旧APIの呼び出しを削除」など)。細かすぎる差分の羅列にせず、レビュアーが要点を掴めるようにする。

本文の例:

```markdown
## 概要
ユーザー登録時のメールアドレス重複チェックを追加した。

## 変更点
- 登録APIにメールアドレスの重複チェックを追加
- 重複時に409エラーを返すように変更
- 対応するユニットテストを追加
```

### 3. PRを作成する

本文に改行や記号を含むため、ヒアドキュメントで渡す(直接 `--body` にベタ書きするとシェルのクォート崩れの原因になるため避ける):

```bash
gh pr create --base "<ベースブランチ名>" --title "<タイトル>" --body "$(cat <<'EOF'
<本文(Markdown)>
EOF
)"
```

- 常に通常のPRとして作成する(`--draft` は付けない)
- ステップ1で `EXISTING_PR:` が出ていた場合はこのコマンドは実行せず、そのURLを案内する
- 本文はステップ2で作成した内容のみとする。`🤖 Generated with [Claude Code]` のような定型の帰属(attribution)表記は追加しない(これを完全に止めるには `.claude/settings.json` 等で `attribution.pr` を空文字に設定するのが確実)

リリースPR(ベースが `main` / `master`)を作成できたら、レビュー済みの記録(`release-review.md` と `MEMORY.md` の索引の行、または `~/.claude/release-review/<リポジトリ名>.md`)を削除する。PRの作成に失敗した場合や、`EXISTING_PR:` で新規作成しなかった場合は削除しない。

### 4. 結果をユーザーに伝える

`gh pr create` の出力にPRのURLが含まれるので、それをそのまま提示する。リリースPRの場合は、レビュー済みの記録を削除したことも伝える。

## エッジケースの扱い

| 状況 | 対応 |
|---|---|
| `gh` 未インストール/未認証 | インストールや `gh auth login` を促して停止 |
| Gitリポジトリでない | エラーを伝えて停止 |
| リモートに指定したベースブランチがない | エラーを伝えて停止 |
| 現在のブランチが指定したベースブランチ自身 | 作業ブランチへの切り替えを案内して停止 |
| ベースブランチとの差分(コミット)がゼロ | 「差分がないためPRの必要はない」旨を伝えて停止(PRは作らない) |
| 未コミットの変更がある | 警告として件数だけ伝え、コミット済みの差分のみでPRを作成する(未コミット分は無視) |
| 同じブランチで既にPRが存在する | 新規作成せず、既存PRのURLを案内する |
