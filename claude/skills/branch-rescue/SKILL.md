# branch-rescue

developブランチのまま気づかずに作業してしまった変更を、developには一切影響を与えずに、適切な名前の新しいブランチへ引き継ぐスキルです。

## いつ使うか

- ユーザーが `/branch-rescue` と入力したとき
- 「developで作業しちゃった」「developのままファイル編集しちゃったんだけど」「間違えてdevelopでコード書いてた、ブランチ分けたい」のように、developブランチのまま変更を加えてしまったことに気づいて相談してきたとき
このスキルの対象は **未コミットの変更(staged / unstaged / untracked)** です。develop に誤って直接コミットしてしまったケース(コミット済みの変更をdevelopの履歴から移す)は対象外です。その場合は取り扱いが変わる(develop側のコミットを打ち消す必要がある)ため、ユーザーにその旨を伝えて別途相談してもらってください。

## なぜこのやり方で安全なのか

現在developにいて、かつdevelopに何もコミットしていない(未コミットの変更だけがある)状態であれば、`git checkout -b <新しいブランチ名>` を実行するだけで:

- 新しいブランチが今のコミット位置(develop の最新コミット)から作られる
- 作業ツリー上の未コミットの変更(staged / unstaged / untracked すべて)はそのまま新しいブランチに引き継がれる
- develop 自体には何もコミットされていないので、develop の履歴・内容は一切変化しない
つまり「developをリセットする」ような操作は不要で、ブランチを切り替えるだけで安全に解決できます。

## 手順

### 1. 状態を確認する

```bash
bash scripts/detect_status.sh
```

このスクリプトが以下を判定・出力します:

- gitリポジトリでない → エラーで停止
- 現在のブランチがdevelopでない → `NOT_ON_DEVELOP:<branch>` を出力して終了(このスキルは不要、その旨をユーザーに伝える)
- developにいるが未コミットの変更が一切ない → `NO_CHANGES` を出力して終了(移すべき変更がない旨をユーザーに伝える)
- developにいて未コミットの変更がある → 以下を出力する
  - 現在のブランチ名
  - 既存のローカル/リモートブランチ名の一覧(命名規則を読み取るための参考情報)
  - developの直近のコミットメッセージ一覧(ブランチ名と同様、命名規則を読み取るための参考情報)
  - `git status --short`
  - staged / unstaged それぞれのdiff統計とdiff本文
  - 未追跡(untracked)ファイルの一覧
### 2. 変更内容からブランチ名を判断する

スクリプトの出力を読んで、**ユーザーに聞かずに**ブランチ名を組み立てます。

1. **このセッションの会話履歴を確認する**: このスキルを呼び出すまでの会話の中で、ユーザーが「何の作業をしていたか」に触れていないか確認する(例: 「ログイン周りのバグを直してた」「新しい検索機能を実装してた」など)。diffは「何を変更したか」しか教えてくれないが、会話には「なぜ・何のために」その変更をしていたかという意図が含まれていることが多く、種類(feature/fixなど)やスラッグの精度が上がる。会話の中に明確な言及があれば、それを最も信頼できる手がかりとして扱う。
2. **命名規則の手がかりを探す**: 「既存のブランチ名一覧」と「developの直近のコミットメッセージ一覧」を見る。マージ済みブランチを削除していく運用のリポジトリでは、ブランチ一覧はmain/develop程度しか残っておらず、これ自体は普通のことで手がかりが無いという意味ではない。その場合はコミットメッセージ側(例: `feat: ○○を追加`, `fix: ○○を修正` のようなConventional Commits風の接頭辞)に同じ語彙(feature/feat, fix, chore, refactor など)が使われていないか確認し、見つかればそれに合わせる。ここで確認するのはあくまで表記スタイル(接頭辞の語彙・区切り方)であり、種類そのものの判断は会話履歴やdiffを優先する。
3. **変更の種類を判断する**: 会話履歴で作業内容が分かっていればそれを最優先にし、分からない、または曖昧な場合はdiffの内容やファイルパスから判断する。新機能追加なら `feature/`、バグ修正なら `fix/`、リファクタリングなら `refactor/`、ドキュメントのみなら `docs/`、テストのみなら `test/`、設定や雑多な変更なら `chore/` を選ぶ。複数の性質が混ざっている場合は、変更量や意図から見て主となるものを選ぶ。手がかりで見つけた接頭辞の語彙(例: `feat` vs `feature`)があればそちらの表記を使う。
4. **内容を表す短い英語スラッグを作る**: 変更の意図を要約し、小文字・ハイフン区切りの短い英単語列にする(例: `add-user-auth`, `fix-null-check-on-login`)。ファイル名やdiffの変数名をそのまま繋げるのではなく、「何をしたか」が伝わる意味のある名前にする。長すぎないよう3〜5単語程度を目安にする。会話履歴でユーザーが使っていた言葉があれば、それを英訳の元にすると意図が伝わりやすい。
5. 最終的なブランチ名は `<種類>/<スラッグ>` の形にする(例: `feature/add-subtract-function`)。
判断したブランチ名は、作成前に一度ユーザーに提示する(例:「`feature/add-user-auth` という名前で新しいブランチを作成します」)。ユーザーから特に反対がなければ次に進んでよい。ここでの提示は確認待ちで止まるためではなく、何をしたかを分かりやすく伝えるための一言で構わない。

### 3. ブランチを作成する

```bash
bash scripts/create_branch.sh "<決めたブランチ名>"
```

このスクリプトは:

- 現在developにいることを再確認する(develop以外にいたら安全のため中断する)
- 指定した名前のブランチが既に存在する場合はエラーで中断する(この場合は別の名前を考えて再実行する)
- `git checkout -b <ブランチ名>` を実行し、未コミットの変更を保持したまま新しいブランチに切り替える
- 切り替え後の `git status --short` と、develop側の最新コミットを表示する(develop側に変更が残っていないことの確認用)
### 4. 結果をユーザーに伝える

以下を簡潔にまとめて報告する:

- 作成した新しいブランチ名
- 新しいブランチに切り替わったこと、変更内容(ファイル一覧)がそのまま引き継がれていること
- develop側には変更が残っておらず、安全な状態のままであること
## エッジケースの扱い

| 状況 | 対応 |
|---|---|
| gitリポジトリでない | エラーを伝えて停止 |
| 現在のブランチがdevelopでない | 「既に作業用ブランチにいるため、このスキルは不要」と伝えて停止 |
| developにいるが未コミットの変更が一切ない | 「移すべき変更がない」と伝えて停止(ブランチは作らない) |
| developに直接コミット済みの変更がある(pushしていないローカルコミット) | このスキルの対象外。develop側の履歴を巻き戻す操作が必要になるため、安易に自動実行せず、その旨をユーザーに伝えて対応方針を確認する |
| 変更が複数の性質(機能追加+バグ修正など)にまたがる | 主となる変更内容で種類を1つ選ぶ。無理に分割しようとしない |
| 提案したブランチ名が既に存在する | `create_branch.sh` がエラーで中断するので、別のスラッグを考えて再実行する |
| リポジトリに `develop` ブランチという概念がなく、`main` や `master` で直接作業している | ユーザーに確認する。このスキルは `develop` を前提にしているため、対象ブランチ名が異なる場合はスクリプトを直接使わず、同様の手順(`git checkout -b <name>`)を手動で案内する |
| マージ済みブランチを削除していく運用で、既存ブランチがmain/develop程度しか残っていない | 想定内の状態。「既存ブランチから規則が読み取れない」ことをもって立ち止まらず、developの直近コミットメッセージや一般的な規則(`feature/`, `fix/`など)から判断して進める |
