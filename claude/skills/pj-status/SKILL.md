# プロジェクト進捗の一覧(pj-status)

`projects.txt`(このスキルのディレクトリ直下)に登録した各プロジェクトについて、git の状態とバックログの残タスクをまとめて表示する。目的は「今どのプロジェクトで何が進行中で、何が残っているか」を一目で把握すること。履歴や推移は扱わず、いつ実行しても現在の状態をその場で調べる。

## 設定ファイル

- `projects.example.txt`: 書き方を示したひな形。git 管理する。
- `projects.txt`: 実際の対象プロジェクトを書く PC ごとの設定。パスにユーザー名やプロジェクト名が含まれ、PC によって内容も違うので、`.gitignore` で git 管理から外している。スキルを更新して書き出し直しても上書きされないよう、スキル本体には含めない。

## 集計はスクリプトで一度に行う

プロジェクトごとに git やファイル読み込みを1つずつ実行すると、そのたびに待ち時間が発生する。集計はこのスキルのディレクトリにある `scripts/collect.sh` が全プロジェクト分まとめて行い、表示用の Markdown を出力するので、基本的に1回の実行で済ませる。

```bash
bash <このスキルのディレクトリ>/scripts/collect.sh [--all] [絞り込み文字列]
```

- 引数なし: 全プロジェクト。未着手タスクは各プロジェクト上位5件まで(バックログは優先度順に並んでいるので、上位が重要なもの)。
- `--all`: 未着手タスクを省略せず全件出す。ユーザーが「全部見せて」「残タスク全部」のように言ったときに使う。
- 絞り込み文字列: 表示名またはパスにその文字列を含むプロジェクトだけを出す。「ダウンローダーの状況」のように特定のプロジェクトを聞かれたときに使う。ユーザーが日本語の通称で呼んでいて一致しない場合は、引数なしで実行して該当しそうなものを選ぶ。

スクリプトは読み取りのみで、リポジトリやバックログを変更しない。

### Windows 側から使うとき

対象のプロジェクトとバックログは WSL 側にあるので、集計は常に WSL の中で行う。Windows の git から `\\wsl.localhost\...` のリポジトリを読むと遅く、「所有者が異なる」として拒否されることもあるため。

- Git Bash(Windows 版 Claude Code の Bash ツール)から `collect.sh` を実行した場合は、スクリプトが自動で `wsl.exe` 経由で WSL 内の `~/.claude/skills/pj-status/scripts/collect.sh` に処理を渡す。上と同じコマンドでよい。
- PowerShell から実行する場合は、`wsl.exe` で直接呼ぶ(引数は末尾に足す):

  ```powershell
  wsl.exe -e bash -c 'exec ~/.claude/skills/pj-status/scripts/collect.sh "$@"' pj-status
  ```

- `wsl.exe` は既定のディストリビューションで実行される。「スクリプトが見つからない」と出たら、WSL 側にこのスキルが `~/.claude/skills/pj-status` として置かれているかを確認してもらう。別の場所なら、環境変数 `PJ_STATUS_WSL_SCRIPT` に WSL 内のパスを指定すれば切り替えられる。
- `projects.txt` も WSL 側のものが使われるので、パスは WSL の形式(`~/...` や `/home/...`)で書く。

### 集計される内容

- 一覧表: ブランチ、未コミットのファイル数、進行中・未着手・完了の件数、最終コミットの時期
- プロジェクトごとの詳細:
  - git: ブランチ、未コミット件数、未push件数(上流ブランチがある場合のみ)、最終コミットの時期と件名
  - バックログ: 進行中タスク(詳細メモの進み具合を「—」の後ろに添える)、未着手タスク、完了件数

バックログは backlog スキルの保存先 `~/.claude/backlog-data/<プロジェクト名>.md` から読む。プロジェクト名はリモート origin のリポジトリ名 → git のトップディレクトリ名 → ディレクトリ名の順に探す。

## 表示のしかた

1. スクリプトの出力をそのまま会話に表示する。内容を書き換えたり要約し直したりはしない(スクリプトの出力が一覧として完成しているので、整形し直すと時間がかかるうえに情報が欠けやすい)。
2. 出力の後に、気づいた点があれば2〜3行の箇条書きで添える。何もなければ添えなくてよい。目を向けると良いのは次のようなもの:
   - 未コミットや未push の変更が残っているプロジェクト(作業の途中で止まっている可能性)
   - 進行中タスクのメモが「コミット待ち」「PR待ち」などで止まっているもの
   - `main` や `develop` のまま未コミットの変更があるもの(ブランチの切り忘れの可能性)
   - 進行中が0件で、未着手に優先度「高」が残っているもの
3. 次に何をするかは提案しない。ユーザーが「次どれをやろう?」のように聞いてきたときだけ、上の観点で候補を挙げる。

## うまくいかないとき

- 「設定ファイルが見つかりません」: まだ `projects.txt` が無い(初回、または別の PC)。対象にしたいプロジェクトのパスをユーザーに聞き、`projects.example.txt` をコピーして `projects.txt` を作り、そこにパスを書いてから実行し直す。ユーザーが自分で書くと言えば、コピーの手順だけ案内する。
- 「登録されていません」: `projects.txt` はあるがパスが書かれていない。上と同じく、対象のパスを聞いて書き足す。
- 「パスが見つかりません」: `projects.txt` のパスの誤りか、プロジェクトの移動・削除が考えられる。どちらかをユーザーに確認する。
- 「バックログがありません」: そのプロジェクトでまだ backlog スキルを使っていないか、バックログのファイル名がプロジェクト名と違う。`~/.claude/backlog-data/` のファイル一覧を見て、名前違いであれば `projects.txt` に「パス | バックログ名」の形で書けば紐づけられると伝える。
- プロジェクトの追加・削除を頼まれたら、`projects.txt` を編集する(`projects.example.txt` はひな形なので触らない)。編集後にスクリプトを実行し直して結果を見せる。
