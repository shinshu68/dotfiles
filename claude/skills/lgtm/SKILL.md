# /lgtm — 動作確認完了の合図

## これは何のためのスキルか

開発作業では、Claude が実装した内容についてユーザーが動作確認を行い、それが完了したことを Claude に伝える瞬間がある。この合図が来たら、Claude は「まだ確認中かもしれない」と迷わず、確認が終わったという事実を前提に次の行動へ進んでよい。`/lgtm` はその合図であり、"Looks Good To Me" の意味で使われる、確認完了・承認を意味する開発者コミュニティの慣用句である。

このスキルの目的は、`/lgtm` を受け取ったときに Claude が毎回自然に、かつ一貫した流れで「確認ありがとう → コミットメッセージの提示」という展開をできるようにすること。1つの作業が終わるたびにコミットする運用のため、次の作業の提示までは行わない。

## トリガー

ユーザーのメッセージが `/lgtm` を含む場合（それだけの場合も、後ろに一言添えられている場合も）。他の表現（「OK」「確認できた」など）には反応しない — `/lgtm` は明示的なコマンドとして扱う。

## やること

`/lgtm` を受け取ったら、以下の順で応答する。

### 1. 何を確認済みとして扱うか、一言で振り返る

直前にユーザーへ依頼した動作確認の対象（実装した機能、修正したバグ、追加したテストなど）を会話履歴から特定し、一文程度で振り返る。長々とした要約は不要 — ユーザーはすでに中身を把握しているので、Claude が「何についての LGTM か」を正しく認識していることが伝わればよい。

### 2. 確認済みの変更を git add する

直前の動作確認の対象となったファイル（実装・修正したファイル、追加したテストファイルなど）を特定し、`git add` する。対象が曖昧な場合や、確認対象外の変更（無関係な作業中のファイルなど）が作業ツリーに混ざっている可能性がある場合は、`git status` / `git diff` で変更内容を確認したうえで、確認済みの範囲だけを `git add` する。プロジェクト全体を無条件に `git add -A` しない。

### 3. コミットメッセージの提案を行う

`/commit-suggest` スキルを呼び出し、今回の変更に対するコミットメッセージを提案する。このプロジェクトには `/commit-suggest` スキルが既に存在する前提で、その指示に従ってコミットメッセージを組み立てること — このスキル自身でコミットメッセージのフォーマットを独自に決め打ちしない。`/commit-suggest` が見つからない・利用できない場合のみ、簡潔な一文でその旨を伝え、代わりに要点だけのコミットメッセージ案を出す。

## 出力の型

厳密なテンプレートは強制しないが、次の3要素は毎回含める。

1. 確認完了の受け止め（何が確認されたか）
2. `git add` した内容（何をステージしたか）
3. コミットメッセージ案（`/commit-suggest` 経由）
例:

> 了解です、ユーザー認証まわりの修正の動作確認ありがとうございます。
>
> `src/auth/login.ts` と `src/auth/login.test.ts` を git add しました。
>
> 今回の変更のコミットメッセージ案です。
> （/commit-suggest の提案をここに）

## 注意点

- `/lgtm` は「確認は終わった」という前提を運んでくるコマンドなので、Claude 側から「本当に確認できましたか？」のように聞き返さない。
- `git add` は確認済みの変更範囲に限定する。作業ツリーに無関係な未確認の変更が残っている場合は、それらを含めずに個別のパスを指定して `git add` する。
- 1つの作業が終わるごとにコミットする運用のため、次の作業の提示や質問はしない。ユーザーから次の依頼があるまで待つ。
- コミットメッセージは必ず `/commit-suggest` に委譲する。フォーマット（Conventional Commits か自由記述かなど）はそのスキルの判断に従う。
