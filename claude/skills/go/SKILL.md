# go — 提案された次の作業を承認して進める

ユーザーは Claude の「次は○○を進めますか？」という問いかけに対して、毎回返答文を書く手間を省くために `/go` を使う。つまり `/go` は「はい、お願いします」の短縮形。ユーザーの意図は「止まらずに進めてほしい」なので、ここで再確認を挟むとこのコマンドの存在意義がなくなる。

## 何を進めるか判断する

直前の Claude の応答（その中の最後の提案・質問）を見て、承認された作業を特定する。

- **提案が1つだけ**（例:「次はログイン画面のバリデーションを実装しますか？」）
  → その作業をそのまま開始する。
- **選択肢が複数あり、番号付き**（例:「1. テスト追加 2. リファクタ」）
  - `/go 2` のように番号が付いていれば、その番号の作業を行う。
  - 番号がなければ、Claude が推奨していたもの、推奨がなければ最初の選択肢を行う。どれを選んだかを冒頭で一言伝える。
- **「AとBどちらがいいですか？」のような方針の質問**
  → 推奨していた方があればそれ、なければ Claude が妥当と考える方を選び、選んだ理由を一文だけ添えて進める。
- **`/go` の後にテキストがある**（例:「/go ただしテストは後回しで」）
  → 提案された作業を進めつつ、そのテキストを追加の指示・条件として反映する。

## 進め方

1. 冒頭で「○○に着手します」と一行だけ述べる（長い前置きや確認は不要）。
2. 実際に作業を行う。「進めますか？」への承認なので、計画を再提示して止まるのではなく、実装・修正・調査などの中身まで行う。
3. 作業が終わったら、いつも通り結果を報告し、必要なら次の提案をしてよい（ユーザーはまた `/go` で答えられる）。

## 例外: 承認対象がはっきりしないとき

直前に提案や質問が見当たらない場合（会話の最初に `/go` が来た、直前の応答が質問で終わっていない など）は、推測で大きな作業を始めない。「何を進めればよいですか？」と短く聞く。これは誤った作業で時間やコードを無駄にしないため。

## 注意

- 承認されるのは「提案していた作業」の範囲まで。`/go` を理由に、破壊的な操作（ファイルの大量削除、force push、本番環境への反映など）を提案に含まれていなかったのに追加で行わない。そうした操作が提案そのものだった場合は、その範囲で実行してよい。
- `/lgtm` は「動作確認済み、コミットへ」の合図であり役割が異なる。`/go` ではコミット処理は行わず、単に次の作業を進める。
