# icon-create

アプリのアイコンを、ヒアリング → 候補作成 → 比較ページで確認 → 修正、という往復で一緒に決めていくスキル。成果物は、確定したアイコンの SVG (`assets/icon/icon.svg`) と、決めた内容のメモ (`assets/icon/icon-spec.md`)。

アイコンは好みの比重が大きく、一度で決まることはまれ。最初の候補は「方向性を探るための叩き台」と考え、反応を受けて絞り込んでいく。また、アイコンは大きく表示して良く見えても、ランチャーやタスクバーの小さいサイズでつぶれることが多い。そのため候補は必ず比較ページで小さいサイズと切り取り後の見え方まで並べて見せ、大きな絵だけで判断させない。

範囲は SVG の確定まで。PNG・ico への書き出し、`flutter_launcher_icons` などによる組み込みは行わない (確定後に別の作業として進める)。

## 1. プロジェクトから分かることを拾う

ヒアリングの前に、次のものを読んでアイコンに関わる情報を拾う。すでに分かることを聞き直すとユーザーの手間になるため。

- CLAUDE.md、docs/plan.md (docs/ 配下に分かれていればその中の概要)、README: アプリの内容・名前・対象プラットフォーム
- テーマ色の定義があればその色: Flutter なら `ThemeData` の `seedColor` や `colorScheme`、Android なら `res/values/colors.xml` や Compose の `Color.kt`、Web なら CSS 変数など。アイコンの色をアプリの色と揃える候補になる
- 既存のアイコン: `assets/icon/` や Android の `mipmap-*`、Windows の `.ico` など。作り直しなら現状を踏まえる (前回このスキルで作った `assets/icon/icon-spec.md` があれば、それを出発点にする)

対象プラットフォームは、構成 (`android/`・`windows/`・`ios/` フォルダ、`pubspec.yaml`、`build.gradle` など) からも判断できる。

## 2. まとめてヒアリングする

拾った内容から、次の項目について推測した候補を作り、一度にまとめて確認する。少しずつ聞くと往復が増えるため。

| 項目 | 内容 |
|---|---|
| アプリの内容 | 何をするアプリか (1〜2文) |
| モチーフ | アイコンに入れるもの (例: 目覚まし時計+太陽)。推測できるなら方向の違う候補を2〜3個挙げる |
| 印象 | 例: 爽やか、シンプル、力強い、かわいい |
| スタイル | フラット / 線画 (アウトライン) / 立体感のあるグラデーション |
| 色 | メインカラーとアクセントカラー (HEX)。テーマ色が見つかればそれを候補にする |
| 文字 | 入れない / 頭文字1文字だけ入れる。小さいサイズで読めなくなるため、基本は入れないほうを勧める |
| 避けたいもの | 例: 似せたくない既存アプリ、使いたくない色 |
| 対象 | Android / Windows / iOS / Web など。切り取り方や小サイズの重要度が変わる |

応答の構成は次のとおり。

1. 推測した内容を上の表の形で示す。根拠 (どのファイルから読み取ったか) を一言添えると、ユーザーが読み違いに気づきやすい
2. モチーフ・色・避けたいもののように自由に答える項目は、本文で「違っていれば教えてください」と尋ねる
3. スタイルと文字の有無のように選ぶ項目は、各選択肢の説明を本文に書き、選ぶ操作だけを AskUserQuestion の質問カードで出す。勧めるものがあれば1番目に置き、本文とカードで並び順を揃える

推測した項目も、返答で触れられなかったものを既定値で決めて進めない。返答が一部の項目にしか触れていなければ、残りを改めて尋ねてから候補作成に進む。推測が当たっているかどうかはユーザーにしか分からないため。

何を作るアプリなのかが資料からも会話からも分からない場合は、推測で埋めずに、まずアプリの内容を本文で尋ねて止まる。

## 3. 候補の SVG を作る

### 置き場所

候補は `assets/icon/drafts/` に `icon-a.svg`、`icon-b.svg` … の名前で作る。修正版は `icon-b2.svg` のように元の記号に番号を付け、前の版を上書きしない (見比べられるようにするため)。

### 方向性をばらす

最初は4案を出し、方向性をばらす。好みが分からない段階で似た案ばかり出すと、反応から得られる情報が少ないため。例えば次の軸で変化をつける。

- モチーフの選び方 (候補のモチーフを変える、2つ組み合わせる、1つだけに絞る)
- 構図 (中央に大きく1つ / 背景の形と一体化 / 一部をはみ出させる)
- 色の使い方 (背景をメインカラーで塗る / 背景は白や薄い色でモチーフに色 / グラデーション)

### SVG の作り方

候補はすべて次の構造で作る。Android の adaptive icon にそのまま分けて使えるようにし、後の書き出しを楽にするため。

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 108 108">
  <defs><!-- グラデーションなど。id は候補ごとに固有にする (例: a-grad) --></defs>
  <g id="background">
    <rect width="108" height="108" fill="#2E7D6B"/>
  </g>
  <g id="foreground">
    <!-- モチーフ -->
  </g>
</svg>
```

- `viewBox` は `0 0 108 108` (Android の adaptive icon の 108dp に合わせた単位)
- `background` は 108×108 全体を塗る。角丸や円にはしない (形は OS がマスクで決めるため)
- `foreground` の重要な部分は、中心 (54, 54) から半径 33 の円の内側 (安全領域) に収める。端末によって外側が切り取られるため。モチーフの外寸はおおむね 44〜60 程度が目安
- 線は太めにする。線幅 4 未満は 48px 表示で細い線 (約 1.8px 未満) になり、ぼやけたり消えたりする
- 細部を詰め込まない。16px では 108 単位の 1 マスが約 0.15px になる。要素は 3〜4 個までが目安
- `<text>` は使わない。フォントは環境によって変わり、書き出し時に崩れるため。文字を入れる場合は図形 (`<path>`) で描く
- `filter` (ぼかし・影)、`mask`、外部画像の参照は使わない。Android の Vector Drawable などへの変換で再現できないことがあるため。影を付けたいときは、半透明の図形を重ねて表す
- グラデーションは使ってよいが、`id` は候補ごとに固有にする

Android 13 以降のテーマアイコン (単色表示) では、`foreground` だけが単色で表示される。モチーフを色の違いだけで描き分けていると単色で潰れるため、形 (シルエット) でも判別できるようにする。比較ページの「単色」の列で確認できる。

特に、白い図形の上に背景と同じ色の図形を重ねて「抜いた」ように見せる描き方は、単色にすると重ねた部分が塗りつぶされて消える (例: 白い水滴の上に緑の双葉を描くと、単色ではただの水滴になる)。抜きは次のどちらかで本当の穴として描く。

- 外形と抜く形を1つの `<path>` にまとめ、`fill-rule="evenodd"` を付ける。抜く形どうしが重なると、重なった部分は穴にならず塗られるので、重ならないように描く
- 重ねる図形の周りに背景が見える隙間 (縁取り) を作る。例: 葉の上に水滴を置くなら、葉に水滴より一回り大きい穴を空け、その中に水滴を置く

### 比較ページを作る

候補を作ったら、同梱のスクリプトで比較ページを作る。

```bash
python3 <このスキルのディレクトリ>/scripts/preview.py assets/icon/drafts/preview.html assets/icon/drafts/icon-a.svg assets/icon/drafts/icon-b.svg assets/icon/drafts/icon-c.svg assets/icon/drafts/icon-d.svg
```

ページには候補ごとに、そのまま表示した各サイズ (192・96・48・32・16px)、Android のマスク (円・角丸・スクワークル) で切り取った見え方、単色表示、暗い背景での見え方が並ぶ。安全領域の表示を切り替えるボタンもある。SVG はページに埋め込まれるため、HTML 1ファイルで完結する。

作ったページはブラウザで開く。WSL では次のように Windows 側のブラウザで開ける。

```bash
explorer.exe "$(wslpath -w assets/icon/drafts/preview.html)"
```

開けない環境では、ファイルのパスを伝えて開いてもらう。

### 自分でも確認する

ユーザーに見せる前に、ページの各列を想定して自分でも確認する (画像として見られる環境なら PNG にして見る)。特に次の点。

- 16px・32px で何のアイコンか判別できるか (つぶれて単なる色の塊になっていないか)
- 円マスクで重要な部分が切れていないか
- 単色でシルエットが判別できるか

問題があれば、見せる前に直す。

## 4. 候補を見せる

応答の冒頭に、ここまでに決まった条件を短くまとめる (例:「条件: 目覚まし時計+太陽 / フラット / #FF8A3D と #FFF4E0 / 文字なし / Android」)。往復が続いても条件を見失わないようにするため、またユーザーが読み違いに気づけるようにするため。

続けて、候補ごとに次を短く書く。

```
### A: 時計の文字盤に昇る太陽
- 狙い: 時計の文字盤の下半分を地平線に見立て、朝の目覚めを表す
- 気になる点: 16px では太陽の光線が消え、時計だけに見える
```

- 「気になる点」は、自分で確認して分かった弱点を正直に書く。ユーザーが判断する材料になるため。なければ省いてよい
- 最後に、反応の返し方を添える (例:「気に入ったもの・違うもの・組み合わせたいものがあれば教えてください。『A の色で C の形』のような指定もできます」)

## 5. 反応を受けて直す

ユーザーの反応から好みを読み取り、次の版に反映する。

- 気に入った候補は、指摘の点を直した版 (`icon-a2.svg` など) を作る。方向性を広げたいと言われたら、その候補の要素を残した別案を加える
- 違うと言われた方向は外す。理由が添えられていれば条件に加える
- 「全部違う」と言われたら、何が違ったのかを推測で決めずに聞く。方向性そのものを読み違えている可能性が高いため
- 比較ページは、今回見てほしい版と、比較に必要な前の版だけを載せて作り直す。版が増えすぎると見比べにくくなるため
- 新しく分かった条件は、次の応答冒頭の条件まとめに反映する

## 6. 確定したら

ユーザーがアイコンを決めたら、次を行う。

1. 決まった SVG を `assets/icon/icon.svg` としてコピーする
2. `assets/icon/icon-spec.md` に、決めた内容を短く残す。後で書き出しや修正をするときに、ヒアリングからやり直さずに済むようにするため

```markdown
# アプリアイコン

- モチーフ: 目覚まし時計の文字盤に昇る太陽
- スタイル: フラット、文字なし
- 色: 背景 #FFF4E0、メイン #FF8A3D、アクセント #3D5AFE
- 対象: Android (adaptive icon)、Windows
- 構造: viewBox 0 0 108 108。`#background` が背景レイヤー、`#foreground` が前景レイヤー (安全領域は中心から半径 33 の円)
- 元にした候補: drafts/icon-a3.svg
```

3. `assets/icon/drafts/` の扱い (残す / 削除する / .gitignore に入れる) をユーザーに確認する。勝手に消さない
4. 保存したファイルを報告し、次の作業として「各プラットフォーム向けの書き出しと組み込み」があることを一言添えて止まる。書き出し・組み込み・コミットはこのスキルでは行わず、ユーザーの指示を待つ
