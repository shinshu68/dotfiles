# retro — プロジェクトの知見を棚卸しする

プロジェクトがひと段落したときに、そのプロジェクトで得た知見のうち **別のプロジェクトでも行動を変えられるもの** を洗い出して出力する。

ユーザーは出力をコピーして dotfiles 側の別セッションに貼り付け、そこで取捨選択してグローバルの CLAUDE.md や project-init のひな形に反映する。このスキル自体はファイルを一切変更しない。

## なぜこの形か

- プロジェクトの CLAUDE.md・docs/・自動メモリ・コミットメッセージには、作業中に足したルールや方針転換の理由が散らばっている。プロジェクトの中にあるうちは、次のプロジェクトでは読まれない。
- グローバルの `~/.claude/CLAUDE.md` に入っているものは、すでに全プロジェクトで効いている。同じことを出力しても取捨選択の手間が増えるだけなので除く。
- 貼り付け先のセッションは、このプロジェクトのことを何も知らない。だから各知見は「そのまま読んで意味が通じる」ように、一般化した言い方と短い根拠をセットで書く。

## 手順

読み取りだけで進める。途中でユーザーに確認を挟まず、最後にまとめて出力する。

### 1. グローバルの CLAUDE.md を読む

`~/.claude/CLAUDE.md` を読む (dotfiles へのシンボリックリンクなので、push 前の変更も含めて今の内容が読める)。中に `@パス` での取り込みがあれば、その先も読む。

これが「反映済みかどうか」の基準になる。読めなかった場合は、除外ができない旨を出力の冒頭に一言書いて、除外なしで進める。

あわせて、`~/.claude/skills/project-init/SKILL.md` があれば読んでおく。project-init が新しいプロジェクトに最初から入れている構成 (CLAUDE.md の節や docs/ の分け方) は、構成のひな形としてはすでに反映済みとみなす。

### 2. プロジェクトの資料を集める

プロジェクトのルート (git のトップディレクトリ) で、次を読む。

- **CLAUDE.md**: ルートのものと、サブディレクトリ (モノレポの各パッケージなど) にあるもの全部。
- **docs/**: 配下の Markdown を全部。量が多い場合は、見出しと、方針・決定・注意点・トラブルシュートにあたる節を優先して読む。
- **自動メモリ**: システムプロンプトで案内されている memory ディレクトリ (通常は `~/.claude/projects/<プロジェクトのパスの / を - にしたもの>/memory/`) の `MEMORY.md` と各ファイル。引き継ぎ用の一時メモ (`handoff.md`) は知見ではないので読まなくてよい。
- **git のコミット履歴**: コミットメッセージには「なぜ変えたか」が書かれているので、方針転換や不具合の原因の宝庫になる。

  ```bash
  git log --no-merges --format='--- %h %ad%n%s%n%n%b' --date=short
  ```

  コミットが多い (目安 150 件超) ときは全部は読まず、次に絞る。
  - 件名に修正・取り消し・方針変更を示すもの (gitmoji の 🐛 🚑 ⏪ ♻️ 🔥、`fix` `revert` `修正` `戻す` `やめる` `変更` など)
  - CLAUDE.md・docs/ を変更したコミット (`git log --no-merges -- CLAUDE.md '**/CLAUDE.md' docs/`)。ルールが足された経緯がわかる

  git リポジトリでない場合は、この項目を飛ばす。

### 3. 知見の候補を拾う

集めた資料から、次の2種類だけを拾う。

**A. 全プロジェクト共通の進め方・注意点**

ある技術やこのプロジェクトの仕様に依存せず、どのプロジェクトでも Claude の行動を変えられるもの。例えば:

- 作業中に何度か起きた失敗や手戻りと、その防ぎ方 (自動メモリやコミットの本文によく残っている)
- ユーザーとの進め方で決まったこと (確認のタイミング、報告の仕方、作業の区切り方など)
- CLAUDE.md に後から足されたルールのうち、プロジェクト固有の名前を除いても意味が残るもの

**B. うまく機能した CLAUDE.md・docs/ の構成**

次のプロジェクトの CLAUDE.md や docs/ を作るときに取り入れたい書き方。例えば:

- 途中で追加され、その後も更新され続けた節やファイル (コミット履歴で追える)。使われていた証拠になる
- 「どのファイルとどのファイルで値をそろえるか」の対応表のように、トラブルを防ぐために足された記述の形
- docs/ の分け方や、CLAUDE.md から docs/ への振り分け方で、読みやすく保てていたもの

ひな形として出すときは、節の名前と「何を書く場所か」を書き、このプロジェクトの中身は書き写さない。

**拾わないもの**

- 特定の技術・ライブラリ・API だけで効くノウハウ (「〇〇の設定では△△が必要」など)。同じ技術を使うときにしか役に立たず、今回の対象外
- このプロジェクトの仕様や、プロジェクト固有の名前を外すと何も残らないもの
- 一度きりの事情 (その日の障害、すでに解消した一時的な制約など)

### 4. 反映済みのものを除く

候補ごとに、手順1で読んだグローバルの CLAUDE.md と照らし合わせる。言い回しではなく、**Claude の行動が変わるかどうか** で判断する。

- 同じ行動をすでに求めている → 除く (出力にも載せない)
- 関連するルールはあるが、今回の知見がそれより具体的・別の場面をカバーしている → 「補強」として残し、どの既存ルールに関係するかを書く。貼り付け先で「既存の行を書き換えるか、別の行にするか」を判断できるようにするため
- 関係するルールがない → 「新規」として残す

構成のひな形 (B) は、project-init の SKILL.md に同じ構成があれば除く。

### 5. 出力する

返答は次の形にする。

1. 一言 (例:「dotfiles 側のセッションに貼り付ける内容です。」)
2. 全文を入れた **コードブロック1つ**。言語指定は `markdown`。中にバッククォート3つが含まれる場合は、フェンスを4つ以上のバッククォートにして崩れないようにする
3. コードブロックの後に、除外した件数を理由ごとに1行ずつ添える。除いた内容の一覧は出さない。聞かれたら答える
   - 「反映済みのため除いたもの: N件」(グローバルの CLAUDE.md と project-init にあったもの)
   - 「技術固有のため除いたもの: N件」(特定の技術・ライブラリだけで効くノウハウ)。ユーザーがこれに気づいて別に拾えるように、0件でなければ書く

コードブロックの中身は次のテンプレートに従う。該当がない節は「該当なし」と1行だけ書く。

```markdown
# <プロジェクト名> の振り返りで得た知見

- 対象: <プロジェクト名> (<主な技術を1行で。例: Flutter の Android アプリ>)
- 実施日: <YYYY-MM-DD>
- 参照: CLAUDE.md, docs/ (<主なファイル名>), 自動メモリ, コミット <N> 件
- グローバルの CLAUDE.md に反映済みのものは除いている

## A. 全プロジェクト共通の進め方・注意点

### A1. <知見を一文で。そのまま CLAUDE.md の1行にできる言い方で>
- 区分: 新規 / 補強 (既存:「<関係するグローバル CLAUDE.md の行の要約>」)
- 反映先の案: グローバル CLAUDE.md の「<節の名前>」
- 背景: <このプロジェクトで何が起きて、この知見になったか。1〜3行>
- 根拠: <ファイル名や節、コミットのハッシュと件名など>

### A2. ...

## B. うまく機能した CLAUDE.md・docs/ の構成

### B1. <構成の名前>
- 区分: 新規 / 補強 (既存: project-init の「<関係する箇所>」)
- 反映先の案: project-init のひな形 (CLAUDE.md の節 / docs/ のファイル)
- 中身: <節の名前と、何を書く場所か。2〜4行>
- 機能していた理由: <なぜ役に立ったか。1〜2行>
- 根拠: <ファイル名や節、コミットなど>
```

書くときのポイント:

- 知見の一文は、プロジェクト固有の名前 (ファイル名、関数名、画面名など) を外し、「どんな場面で・何をするか」の形にする。具体的な名前は「背景」と「根拠」に回す。貼り付け先でそのまま CLAUDE.md の1行として使えるようにするため。
- 「背景」は、貼り付け先のセッションがこの知見を採るかどうか判断するための材料。このプロジェクトを知らない人にも通じるように書く。
- 根拠のない推測で知見を作らない。資料に書かれていること、コミット履歴から読み取れることだけを使う。
- 件数は絞る。A・B それぞれ多くても 8 件程度を目安にし、効果が大きそうなものから並べる。どれも小粒なら少なくてよく、0 件でもよい。水増しすると取捨選択の手間が増えるだけなので。
- 括弧は半角の () を使う。

## 修正を頼まれたとき

同じ会話で「A3 は要らない」「もっと短く」などと言われたら、資料を読み直さずに直し、全文を同じ形のコードブロックで出し直す。貼り付け直す手間を減らすため、差分ではなく全文を出す。
