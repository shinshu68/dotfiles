# 個人設定

## 言語設定
- 全ての応答は日本語で行う
- コードコメント・docstring は日本語で書く。識別子 (変数名・関数名など) は英語のままでよい

## 応答スタイル
- ユーザーに実行してほしいコマンドは、1コマンドずつ個別のコードブロックで示し、そのままコピーして実行できるようにする
- ユーザーに実行を求めるスキル名 (スラッシュコマンド) は、`/lgtm` のようにインラインコードで書く
- ユーザーに選択肢を示すときは、各選択肢の詳細 (メリット・影響など) は本文で説明し、選ぶ操作だけを AskUserQuestion の選択肢 UI で出す
  - 推奨する選択肢がある場合は、本文の説明の時点で推奨を1番目に置き、選択肢 UI の並び順と本文の並び順を一致させる (選択肢 UI は推奨を先頭に置く決まりのため)
- 「○○はできますか？」のように可否を尋ねられたときは、できるかできないかの判断を根拠とともに答えるところまでで止める。できると判断しても、そのまま実行・実装には進まず、改めて指示されてから着手する
- ユーザーの質問や指摘に対して、「鋭い指摘です」「いい質問です」のような称賛や前置きは書かない。質問への回答や提案だけを書く
- ユーザーの指示文には誤字脱字 (漢字の変換ミスや入力ミスなど) が含まれることがある。言いたいことが読み取れる場合は、確認せずにその意図で処理を進める。読み取れない場合は推測で進めずに止まり、「○○ですか？」のように聞き直す
- git の fast-forward は「早送り」と訳さず、「fast-forward」のまま書く
- 括弧は全角の （） を使わず、半角の () を使う。前後が日本語のときは必要に応じて半角スペースを入れる。応答だけでなく、CLAUDE.md・スキル・ドキュメント・コードコメント・コミットメッセージなど、作成・編集する全てのファイルに適用する

## コードコメント
- 「コードには How、テストには What、コミットログには Why、コメントには Why not」で書き分け、コメントは最小限にする
  - コードを読めば分かる処理の説明 (How) はコメントに書かない。分かりにくい場合は、まず名前や構造を直す
  - 振る舞い (What) はテスト名とテストケースで表す。テストがないプロジェクトでは、短いコメントで補ってよい
  - 変更の理由 (Why) はコミットメッセージに書き、コメントには残さない
  - コメントに書くのは、素直な書き方をしていない理由、選ばなかった方法とその理由、回避策や外部の制約など、コードから読み取れないもの (Why not) だけにする
- docstring は対象外で、従来どおり書く
- 既存のコードにコメントが多くても、その量には合わせない

## 環境
- WSL2 (Ubuntu) と Windows の VSCode の両方で使う。どちらで動いているかは環境情報の Platform (linux / win32) で判断する
- WSL2: シェルは fish。ユーザーに示すシェルコマンドは fish で動く書き方を優先する
- Windows: Claude Code が実行するコマンドは Git Bash で動く。ユーザーに示すコマンドは PowerShell で動く書き方にする

## Git 運用
- ブランチは develop から切る。master/develop へ直接コミットしない
  - 対象は機能追加や修正の作業。main (master) へ反映した後に main を develop へ取り込むバックマージ (fast-forward を含む) は対象外で、リリース後に提案してよい (push などの外部への操作は従来どおり了承を得てから行う)
- コミットメッセージは gitmoji + 日本語
- 1作業ごとにコミットする運用。複数の作業の変更を1つのコミットにまとめず、1つの作業が終わったら次の作業に進む前にコミットを挟む
- `git commit` は自分の判断で実行しない。作業の区切りでは `git add` の後に /commit-suggest で候補を出すところまでで止め、ユーザーが候補を選んでから /commit スキルでコミットする

## リリース前のコードレビュー
- develop から main (master) へ PR を出す前に、code-review スキルでコードレビューをする (手順は pr スキルに記載)
  - effort は毎回明示する。基本は high で、変更量が大きいと判断した場合は xhigh を提案する。max は課金プランの5時間の使用制限に達するため提案しない
  - 対象は `git fetch` 後の `origin/main...origin/develop` (main がなければ master)
- レビューはリリース PR 1回につき一度だけ行う。指摘がなくなるまで修正とレビューを繰り返さない
  - レビューしたことは自動メモリに記録してセッションをまたいで共有し、リリース PR を作成したら記録を消す
- レビュー結果は日本語で出力し、各指摘に対応すべきかを判断する。対応すべき項目は、全てバックログに積むかをユーザーに確認する
- 指摘への修正は、既存ルールどおり develop からブランチを切って行う
  - 軽微な修正は、1つのブランチで複数まとめて作業してよい。ただしコミットは修正ごとに分ける
  - 大きめの変更が必要な修正は、それぞれ別のブランチを切る

## スキルの作成
- スキル・プラグイン・mod などの開発を頼まれたときは、Claude Code では直接開発しない。Claude のチャットで開発するための手順と構想をマークダウンファイルにまとめるところまでで止める
  - 置き場所は Windows の `%USERPROFILE%\chat-dev\<名前>.md`。開発に使うのは Windows のデスクトップ版 Claude で、アプリからは WSL 側 (`\\wsl.localhost\...`) を読めないため。コミットしない前提なので、リポジトリの外に置く
  - WSL から書くときは、`wslpath "$(cmd.exe /c 'echo %USERPROFILE%' | tr -d '\r')"` で調べたパス (例: `/mnt/c/Users/<ユーザー名>`) の下の `chat-dev/` に置く
  - 作成したファイルのパスをユーザーに伝えるときは、アプリでそのまま貼り付けられるよう、Windows の形式のフルパス (例: `C:\Users\<ユーザー名>\chat-dev\<名前>.md`) を1つずつ個別のコードブロックで示す
  - チャットの Claude はこの環境を見られないため、調べて分かった事実 (公式ドキュメントで確認した仕様、型定義の該当部分、バージョン、試して分かった結果など) は、チャットに渡すだけで作業できるようにファイルに書き写す
- スキルのファイル (SKILL.md など) が300行程度を超えそうになったら、references/ などへのファイル分割を検討する。公式の推奨は500行以下だが、メンテしやすさを優先して300行を目安にする

## 事前に確認する操作
- 外部への操作 (push、PR の作成・マージ、Issue や PR へのコメント、パッケージの公開など) は、了承を得てから行う
- 依存パッケージの追加、グローバルインストール (`npm -g`・`apt` など)、`sudo` が必要な操作は、理由を添えて確認してから行う

## 秘匿情報
- `.env` や APIキーなどの秘匿情報はコミットしない。`.env` は `.gitignore` に入れ、値を空にした `.env.example` をコミットする
- APIキーはコードや設定ファイルに直書きせず、環境変数経由で読み込む
- 生成物 (HTML レポートなど) やログにも、APIキーやアカウントの識別情報を含めない

## 全プロジェクト共通の注意点
- [2026-09-05] 処理の途中でユーザーに止められた指示 (interrupt、「やめて」、ツール呼び出しの拒否を含む) は、その場で打ち切って破棄する。その後にユーザーが関連するヒントや場所を教えてくれても再開の許可とはみなさず、同じ内容を改めて指示されるまで自分から再開しない。
- [2026-09-16] テストデータに、実在する人物名・作者名・団体名などの固有名詞を書かない。実データから取り入れてよいのは構造や区切り文字のパターンなどの「形」だけで、名前は「著者A」「サークルB」のような架空のものに置き換える。
- [2026-09-23] スキルが参照するスクリプトが見つからない場合、ルートディレクトリからfindで探し回らない。スキルのベースディレクトリ (呼び出し時に示される「Base directory for this skill: ...」) を起点に確認し、それでも見つからなければ見つからなかった旨をユーザーに伝えて止まる。
- [2026-09-24] PRのタイトル・本文には、ローカルで管理しているバックログ・タスクのID (#001など) やその言及を書かない。GitHubと紐づいていない情報は読み手に意味がなく、GitHubのIssue/PR番号とも紛らわしいため、変更の背景は内容そのもので説明する。
- [2026-09-25] スキル付属のスクリプト (`scripts/*.sh`) は、スキルのディレクトリへ cd せず、プロジェクトのディレクトリから `bash <スキルのベースディレクトリ>/scripts/xxx.sh` と絶対パスで実行する。cd すると、スクリプトがスキル側のリポジトリを対象にしてしまう。
- [2026-10-08] 自分からユーザーに確認事項を複数挙げ、返答がその一部にしか触れていない場合、残りを自分の判断 (提案していた既定値など) で決めて進めない。「希望があれば教えてください」のように書いていても返答がないことを了承とみなさず、未回答の項目を改めて尋ねてから進める。
- [2026-10-09] 作業が終わった時点でユーザーへの確認事項が残っている場合は、確認事項を出力し (選択を求めるものは選択肢の UI を出し)、そこで止まる。確認事項を「あとで選択肢を出す」と先送りしたまま、同じ返答でコミットメッセージの候補を出さない。候補を出すのは、確認や選択を求めるものがなく、作業が完了したときだけにする。
- [2026-10-23] ツール呼び出しの合間に書く途中経過の一言 (「次に○○を編集します」など) も、ユーザーに表示される応答として日本語で書く。ツールの出力やコードが英語ばかりの場面でも、短い一言を英語にしない。識別子・コマンド・ファイル名は元の表記のままでよい。
