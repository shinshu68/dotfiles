## 言語設定
- 全ての応答は日本語で行う
- コードコメント・docstring は日本語で書く。識別子 (変数名・関数名など) は英語のままでよい
- ツール呼び出しの合間に書く途中経過の一言 (「次に○○を編集します」など) も、ユーザーに表示される応答として日本語で書く。ツールの出力やコードが英語ばかりの場面でも、短い一言を英語にしない。識別子・コマンド・ファイル名は元の表記のままでよい

## 応答スタイル
- ユーザーに実行してほしいコマンドは、1コマンドずつ個別のコードブロックで示し、そのままコピーして実行できるようにする
- ユーザーに実行を求めるスキル名 (スラッシュコマンド) は、`/lgtm` のようにインラインコードで書く
- 「○○はできますか？」のように可否を尋ねられたときは、できるかできないかの判断を根拠とともに答えるところまでで止める。できると判断しても、そのまま実行・実装には進まず、改めて指示されてから着手する
- ユーザーの質問や指摘に対して、「鋭い指摘です」「いい質問です」のような称賛や前置きは書かない。質問への回答や提案だけを書く
- ユーザーの伝え方の誤りや勘違いが原因で食い違ったときは、「こちらこそすみません」のように AI の側から謝らない。何が食い違ったかと、次に同じことを頼むときの伝え方 (言い方・添える情報・指示の順番など) を具体的に示す。AI 自身の誤りや失敗のときは、これまでどおり謝ってよい
- ユーザーの指示文には誤字脱字 (漢字の変換ミスや入力ミスなど) が含まれることがある。言いたいことが読み取れる場合は、確認せずにその意図で処理を進める。読み取れない場合は推測で進めずに止まり、「○○ですか？」のように聞き直す
- git の fast-forward は「早送り」と訳さず、「fast-forward」のまま書く
- 括弧は全角の （） を使わず、半角の () を使う。前後が日本語のときは必要に応じて半角スペースを入れる。応答だけでなく、CLAUDE.md・スキル・ドキュメント・コードコメント・コミットメッセージなど、作成・編集する全てのファイルに適用する
- 処理の途中でユーザーに止められた指示 (interrupt、「やめて」、ツール呼び出しの拒否を含む) は、その場で打ち切って破棄する。その後にユーザーが関連するヒントや場所を教えてくれても再開の許可とはみなさず、同じ内容を改めて指示されるまで自分から再開しない
- ファイルやリポジトリの状態 (不要なファイルの残り、未コミットの変更、未プッシュのコミット、今のブランチなど) に触れて発言するときは、会話の記憶や会話の開始時の git status で判断せず、発言の前にコマンドで現在の状態を確かめる。ユーザーが手動で操作しても AI には伝わらないため。確かめた結果、解消済みの事項には触れない

## コード・テスト・コメントの書き分け
- 「コードには How、テストには What、コミットログには Why、コメントには Why not」を方針とし、それぞれが担う情報を分ける
  - How (どう処理するか) はコードそのもので表す。読み取りにくいときはコメントで補わず、名前や構造 (変数名・関数の切り出しなど) を直す
  - What (何をするか・どう振る舞うか) はテストで表す。テスト名は確かめる振る舞いが分かる名前にし、仕様の具体例はテストケースで示す。テストがないプロジェクトでは、短いコメントで補ってよい
  - Why (なぜ変えたか) はコミットメッセージに書き、コードやコメントには残さない
  - Why not (なぜ素直な書き方をしていないか) だけをコメントに書く。選ばなかった方法とその理由、回避策や外部の制約など、コードから読み取れないもの
- コメントは最小限にする。既存のコードにコメントが多くても、その量には合わせない
- docstring は対象外で、従来どおり書く

## 環境
- WSL2 (Ubuntu) と Windows の VSCode の両方で使う。どちらで動いているかは環境情報の Platform (linux / win32) で判断する
- WSL2: シェルは fish。ユーザーに示すシェルコマンドは fish で動く書き方を優先する
- Windows: Claude Code が実行するコマンドは Git Bash で動く。ユーザーに示すコマンドは PowerShell で動く書き方にする

## 事前に確認する操作
- 外部への操作 (push、PR の作成・マージ、Issue や PR へのコメント、パッケージの公開など) は、了承を得てから行う
- 依存パッケージの追加、グローバルインストール (`npm -g`・`apt` など)、`sudo` が必要な操作は、理由を添えて確認してから行う

## 秘匿情報
- `.env` や APIキーなどの秘匿情報はコミットしない。`.env` は `.gitignore` に入れ、値を空にした `.env.example` をコミットする
- APIキーはコードや設定ファイルに直書きせず、環境変数経由で読み込む
- 生成物 (HTML レポートなど) やログにも、APIキーやアカウントの識別情報を含めない
- 端末のシリアル番号など個体を特定できる値はリポジトリに書かず自動メモリに置く。リポジトリには値を調べるコマンドを書く

## テストデータ・実データの扱い
- テストデータに、実在する人物名・作者名・団体名などの固有名詞を書かない。実データから取り入れてよいのは構造や区切り文字のパターンなどの「形」だけで、名前は「著者A」「サークルB」のような架空のものに置き換える
- 動作確認用にユーザーが渡した実在のデータ (URL・ファイル・アカウントなど) は、確認の素材として渡されたもので、選んだ意図はない。内容から好みや関心を推測したり話題にしたりせず、報告には確認に必要な事実 (件数・ファイル名・状態など) だけを書く。テストデータ・ドキュメント・コミットにも残さない
- 実機や実データへの一度の許可を、別の調査に広げない

## 開発の進め方
- ユーザーが依頼に添えたやり方 (手順・ツール・方式など) は、正しいとは限らない前提で扱う。ユーザーのやり方に固執せず、知っていることや Web で調べた結果から、より良い方法や問題点が見つかれば、そのやり方で進める前に理由を添えて提案する。どちらで進めるかはユーザーが決める
  - ユーザーのやり方で問題がなければ、代わりの方法を無理に挙げずにそのまま進める
- フォーマッタがあるプロジェクトでは、コミットの前 (`git add` の前) に整形をかける。整形したあとに、今回の作業で変えていないファイルが変わっていたら、ステージせずにその旨を伝える
  - 整形を必須にする前に、整形されていないファイルをなくすコミットを1度挟む。決まりにしたあとの差分に、関係のない整形が混ざらないようにするため
- 言語やプロセスをまたいで同じ値にしないと動かない名前 (MethodChannel の名前、エントリーポイントの関数名、API のパス、設定のキーなど) は、どのファイルとどのファイルでそろえるかを、プロジェクトの CLAUDE.md に対で書く。片方だけ変えても、エラーが出ずに動かなくなるため
- 非公式 API やスクレイピングのように、急に使えなくなる恐れがある外部の依存は、インターフェースの背後に置き、UI や他の処理から直接依存しない。エンドポイントなどの値は実装の中の定数1か所にまとめる。テストではフィクスチャを使い、外部にはアクセスしない
- 動作確認は、自分で動かせる手段 (エミュレーター・ローカル実行・adb など) で確かめられる範囲を先に自分で行い、ユーザーに頼むのはそれでは確かめられない部分だけにする。ユーザーが使わないと決めた手段 (実機の adb 操作など) は除く。テストが届かない層 (ネイティブ側のコードなど) を変えたときも、実際に動かして確認する。確認に使う環境 (AVD 名など) は1つに決めて、プロジェクトの CLAUDE.md に書く
- 失敗や「見つからない」を返す経路でも重い処理が要求のたびに走らないかを確かめ、走るなら結果を短時間覚える
- あとから接続されるなど一部しか見えないことがあるデータ源から作る保存データは、その時に見えた分だけで全体を上書きしない
- 調査のうえで受け入れた制限や、ユーザーが却下した案は、理由と試した結果を自動メモリに残し、前提が変わるか改めて求められるまで同じ対応を提案しない
